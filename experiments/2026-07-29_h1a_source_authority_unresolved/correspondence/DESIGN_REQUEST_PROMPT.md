# H1a 설계 판정 요청 — 다른 workspace/외부 수신자용 프롬프트

> **사용법**: 아래 첫 `---` 부터 마지막 `---` 까지 전체를 복사해 설계 담당에게
> 그대로 전달한다.
>
> **수신자 유형과 무관하게 하나로 동작한다**:
> - 파일 접근이 **없는** 수신자(외부 AI, 사람) → 본문 M1~M10만으로 판정 가능.
>   부록 A는 무시하면 된다.
> - 파일 접근이 **있는** 수신자(같은 머신의 다른 workspace) → 부록 A의 읽기 전용
>   명령으로 실측을 직접 재현할 수 있다.
>
> 저장소를 상시 다루는 내부 세션에는 대신 `DESIGN_REQUEST.md`를 준다.
> 내용은 같고, 그쪽이 파일 참조 중심으로 더 조밀하다.

---

당신은 **ConceptGate 프로젝트의 실험 설계 판정 담당**이다. 아래 실험(H1a)에
대해 **설계 판정 7건**을 내려 달라. 당신의 판정은 구속력이 있으며, 운영
세션은 그대로 따른다.

## 0. 먼저 알아야 할 것

- **이 프롬프트는 저장소 접근 없이 판정할 수 있도록 작성됐다.** 판정에 필요한
  사실은 전부 아래에 실측값(M1~M10)으로 적혀 있다. 이 값들은 운영 세션이 실제로
  코드를 실행해 측정한 것이며 그대로 사실로 받아들여도 된다.
- **필요한 사실이 아래에 없으면 추측하지 말고 "이 정보가 필요하다"고 물어라.**
  없는 사실을 가정하고 내린 판정은 이 프로젝트에서 반복적으로 사고를 냈다.
- 본문에 파일 경로가 나오면 그것은 **출처 표시**다. 열어보지 않아도 판정할 수 있다.
- **다만 당신이 이 머신의 파일을 읽을 수 있는 환경이라면**(다른 workspace의
  Claude Code 등), §부록 A의 읽기 전용 명령으로 M1~M9를 직접 재확인할 수 있다.
  이 프로젝트의 교차 확인 원칙은 "어떤 주장이든 실제 관측 경계에서 재확인한다"이므로
  **가능하면 확인하는 쪽을 권한다.** 확인하든 안 하든 판정 자체는 가능하다.
- **어느 경우에도 파일을 수정하거나 커밋·푸시하지 마라.** 당신의 산출물은
  §회신 형식의 판정문 하나다.

## 1. 실험이 묻는 것

**가설**: stale(낡은) 문서와 live(살아 있는) 코드가 **같은 인스턴스**에 대해
서로 다른 분류를 주장할 때, LLM 클라이언트는 어느 쪽이 더 권위 있는지를
**스스로 판정하지 않고 보류하는가?**

이 프로젝트는 자연어를 evidence-carrying 개념으로 고정한 뒤 is-a 계층을
결정론적 게이트가 판정하는 시스템이다. LLM은 "제안"하고 결정론이 "판정"한다.
H1a는 그 LLM이 **출처의 권위를 스스로 서열화하는지**를 본다.

## 2. 왜 이게 별도 실험인가 — 구조적 긴장

선행 실험 E2.4는 이 행동을 **금지**했다. 계약 프롬프트 서문이 모델에게 이렇게
지시한다:

> 이 packet의 evidence item은 실행 전 provenance/eligibility 검증을 통과했다.
> **모델은 출처의 liveness나 우선순위를 재판정하지 않는다.**

그리고 채점 규칙 #11이 위반을 **오답으로** 채점한다:

> The model does not adjudicate source liveness or precedence; a rationale that
> decides between two items on the grounds that one source is newer, still in
> use, or more authoritative is out of contract and **must be scored as such**
> rather than credited as a conflict resolution.

또한 외부 운영 지시(2026-07-29) §3이 이 축을 E2.4에서 분리하라고 명령했다:

> stale source와 live source의 권위 충돌은 E2.4 conflicting_evidence로
> 처리하지 않습니다. 이는 향후 별도 source_authority_unresolved 실험
> 대상입니다.

**요점**: E2.4에서 이 행동은 "측정 대상"이 아니라 "금지 사항"이다. H1a는 같은
행동을 측정하려 하므로 계약·스키마·채점기를 그대로 재사용할 수 없다.
**어디까지 바꿀 것인가가 당신이 판정할 내용이다.**

## 3. 실험 재료 (확보·검증 완료)

인스턴스가 `칼`/`철`로 **정확히 일치**하는 실제 충돌이다. 합성한 것이 아니라
이 저장소에 원래 있던 텍스트다.

| 측 | 원문 | 주장 |
|---|---|---|
| **stale 문서** | `(4) 재료-대상: 철은 칼의 재료 → essential_feature (재료는 본질이 될 수 있음)` | 철 = `essential_feature` |
| 〃 (같은 문서, 4줄 뒤) | `주의: 재료-대상(4)만 essential_feature가 될 수 있습니다.` | 예외임을 강조 |
| **live 코드** | `"material_of": "structural_composition",  # Winston stuff-object (has-a)` | 철 = `structural_composition` |
| **통과 중 테스트** | concept `칼`, feature `철`, type `structural_composition`, `relation_hint="material_of"` | live 쪽을 회귀로 고정 |

**문서가 낡았다는 근거**: 그 문서의 마지막 변경은 패키지 리팩터 커밋으로,
상단에 경고 배너만 추가했고 **본문 주장은 손대지 않았다.** 이후 코드가 반대
방향으로 확정됐다.

**검증 상태**: 독립 리뷰어가 위 4행과 이력 주장을 전수 확인했고, 테스트는
실제로 실행해 통과를 확인했다.

## 4. 실측 사실 (M1~M10) — 판정의 근거. 그대로 받아들여도 된다

| # | 실측 |
|---|---|
| **M1** | evidence의 "적격성 프로필"(출처 종류를 하네스가 분류한 값)은 **모델에게 전달되지 않는다.** 4종 값 전부 모델 입력에 부재함을 확인했다 |
| **M2** | 반면 `source_kind`는 **모델 입력에 포함되며** 가능한 값은 `code` / `doc` / `test` / `fixture` / `commit_message` 다. 즉 **"문서 vs 코드" 구분은 모델에게 이미 주어져 있다** |
| **M3** | `docs/` 경로를 받아들이는 분기를 추가해도 E2.4의 동결 해시(렌더된 프롬프트·모델입력·검증매니페스트)는 **3개 fixture 전부 불변**이고 동결본과 일치했다 |
| **M4** | 스키마 파일에 **arm별 스키마 매핑이 이미 존재**한다: `{CONTROL_REPO→legacy, A_REPO→legacy, CONTRACT_REPO→evidence_contract_v1}`. arm별 분기는 새 개념이 아니다 |
| **M5** | legacy 스키마의 `decision` 선택지는 `report_done` / `repair` / `request_evidence` 뿐이다 — **"보류(abstain)" 어휘가 아예 없다** |
| **M6** | 기존 계약 스키마(`evidence_contract_v1`) **본체**를 수정하면 시험 대상 agent 정의 파일이 stale이 되어 **테스트가 실패하고 동결 절차가 거부된다**(하드 브레이크) |
| **M7** | 반면 **새 variant 추가**·arm 매핑 항목 추가·채점규칙 배열 수정은 그 파이프라인을 건드리지 않아 **테스트가 통과**한다 |
| **M8** | 스키마 파일 전체 해시는 어느 편집이든 바뀌지만, **그 값을 재검증하는 코드가 없다**(동결 대조는 렌더된 프롬프트 해시만 본다). 즉 런타임 실패는 없고 **provenance 주장만 약해진다** |
| **M9** | 채점 규칙 11개는 **arm 조건이 없는 평평한 배열**이고, 채점 함수는 arm 인자를 받지 않는다 |
| **M10** | 위 §3 재료 주장 10건 중 9건이 독립 검증에서 CONFIRMED (나머지 1건은 아래 §5에서 처리됨) |

## 5. 이미 결론난 것 — 재론하지 말 것

이 실험의 최초 초안은 **"실험이 성립 불가일 수 있다"**고 주장했다. 근거는
*"낡은 문서임을 표시하면 모델에게 정답을 알려주는 꼴이고, 표시하지 않으면
모델이 두 텍스트를 구분할 수 없다"* 였다. **두 갈래 모두 사실이 아니었다**:

- M1 — 적격성 프로필은 애초에 모델에 전달되지 않는다. "표시하면 유출"은
  **구조적으로 불가능한 시나리오**였다.
- M2 — `source_kind`로 `doc` vs `code` 구분이 **이미 주어진다.** "구분 불가"도
  틀렸다.

또한 적대 검증에서 제기된 blocker 2건("스키마 확장이 동결 해시를 깬다",
"지시문 인용이 틀렸다")도 재실측으로 **둘 다 기각**됐다.

**이 프레이밍으로 되돌아가지 마시라.** 잘못된 전제 위의 판정을 막기 위해
오류 경위를 그대로 남긴다.

# 판정 요청 7건

각 항목에 **선택지 표**와 **실측 제약**이 있다. 운영 세션의 **권고**도 적었으나
**비구속이며 무시해도 된다** — 다른 결론을 내려도 그대로 따른다. 권고를 먼저
읽고 싶지 않다면 건너뛰어도 판정에 지장이 없도록 분리해 두었다.

## 【선행 1】 D-H1a-4 — 채점 극성: 독단 해결은 정답인가 오답인가

**질문**: 금지 조항을 제거한 arm에서 모델이 "코드가 살아 있으니 코드를 택한다"고
판단했을 때, 그 시행을 **성공으로 채점하는가 실패로 채점하는가?**

**왜 결정 사항인가**: E2.4는 극성이 명확하다(#11 위반 = 오답). H1a는 같은
행동을 **측정 대상**으로 바꾸므로 극성이 자동으로 정해지지 않는다. 초안은
"독단 해결 = 나쁜 신호"로 읽히지만 어디에도 고정돼 있지 않다.
**해석 기준이 사전에 없으면 무엇이 관측되든 사후 설명이 가능해진다.**

| 안 | 채점 규칙 | 답하는 질문 | 위험 |
|---|---|---|---|
| **A** 보류=정답 | 보류만 통과, 독단 해결은 실패 | "계약 없이도 스스로 자제하는가" | 금지 조항을 **뺀** arm에서 자제를 요구하는 게 공정한가 |
| **B** 보류=오답 | 우열 판정하되 **근거를 evidence에서 대는 것**만 통과 | "판정을 시키면 근거 있게 하는가" | E2.4 #11과 정면 배치. 같은 저장소에 반대 극성 공존 |
| **C** 극성 없음(서술적) | 정답/오답 없이 **행동 분포**만 기록 | "무엇이 일어나는가"(탐색적) | 기존 인증 체계(합격 임계 0.90, 3구간 밴드) 사용 불가 |
| **D** arm별 분리 | 금지 유지 arm은 A, 제거 arm은 C | 두 질문을 한 실험에서 | 채점기가 arm별로 달라짐 → D-H1a-3와 결합 |

**실측 제약**: M9(채점 규칙이 arm 조건 없는 평평한 배열, 채점 함수가 arm을
받지 않음) — A·B를 arm별로 다르게 적용하려면 채점기 구조 변경이 필요하다.
C를 택하면 기존 인증 체계를 못 쓰므로 "이 실험은 무엇으로 종료되는가"를 따로
정의해야 한다.

> **권고(비구속)**: C 또는 D. H1a는 아직 "무엇이 옳은 행동인가"에 대한 사전
> 지식이 없다. E2.4는 옳은 행동을 계약으로 **정의한 뒤** 준수를 측정했지만,
> H1a는 그 정의 자체가 열려 있다. 극성을 지금 못박으면 측정이 아니라 가정이
> 된다. 다만 C는 종료 조건을 따로 정의해야 하므로 D가 절충이다.

**미판정 시**: D-H1a-2와 D-H1a-3을 결정할 수 없다.

## 【선행 2】 D-H1a-6 — arm 개수: 3개인가 2개인가

**질문**: legacy 프롬프트를 쓰는 `CONTROL_REPO` arm을 유지하는가, 아니면
"금지 유지" / "금지 제거" 2개로 축소하는가?

**왜 결정 사항인가**: 초안은 3-arm을 제안했으나 필요성을 논증하지 않았다.
이 프로젝트의 코드 철학 1번은 **YAGNI — "이게 존재할 필요가 있는가?"** 이고
"요청되지 않은 추상화 금지"가 명시돼 있다.

| 안 | 구성 | 분리되는 변수 |
|---|---|---|
| **A** 3-arm 유지 | CONTROL(legacy) + 금지유지 + 금지제거 | 계약 유무 + 금지조항 유무 |
| **B** 2-arm 축소 | 금지유지 + 금지제거 | 금지조항 유무만 |
| **C** 3-arm이되 CONTROL을 legacy가 아닌 "계약 없는 같은 스키마"로 | 동일 스키마 + 계약문구 없음 | 계약 유무를 같은 스키마 위에서 |

**실측 제약 (결정적)**: **M5** — legacy 스키마에는 **"보류" 어휘가 아예 없다**
(`report_done`/`repair`/`request_evidence`). H1a의 핵심 관측이 "보류하는가"인데
CONTROL arm은 **보류를 표현할 수단이 구조적으로 없다.** 그 arm에서 나온
"보류하지 않았다"는 관측은 모델의 행동이 아니라 스키마의 제약일 수 있다.
(E2.4가 이미 같은 문제를 기록해 두었다.)

> **권고(비구속)**: B. M5 때문에 CONTROL arm의 관측은 해석 불가능하다. 가설은
> 2-arm 대조로 직접 답할 수 있다. 기저선이 꼭 필요하면 A보다 C가 낫다(같은
> 스키마 위에서 계약 유무만 바뀌므로 교란이 적다).

**미판정 시**: D-H1a-3·5의 범위가 확정되지 않는다(2-arm이면 둘 다 작아지거나 소멸).

## D-H1a-1 — 코드 분기를 어디에 넣는가

**질문**: 낡은 문서(`docs/` 경로)를 evidence로 받아들이는 분기를 **E2.4의 동결된
코드에 직접 추가**하는가, **H1a 전용 사본**을 두는가?

**왜 결정 사항인가**: 현재 하네스는 `docs/` 경로를 **거부**한다("소스는 라이브
패키지 코드, 테스트, 동결 실험 아티팩트, 커밋 기록이어야 한다"). 이건 버그가
아니라 E2.4의 **의도된 제약**이다 — 권위 판정을 모델 이전 단계에서 끝내려고
소스를 좁혔다. H1a는 낡은 문서를 써야 하므로 분기가 필요하다.

여기서 두 규칙이 충돌한다:
- **방법론 규칙**: 동결 아티팩트는 실험별로 고정되고 소급 수정하지 않는다
- **코드 철학 2번**: "이미 코드베이스에 있으면 재사용하라"

| 안 | 내용 | 비용 |
|---|---|---|
| **A** E2.4 코드 직접 수정 | 새 프로필 추가 | 한 벌 유지. 동결본 소급 수정(방법론 위반 소지) |
| **B** H1a 폴더에 사본 | 복사 후 분기 추가 | E2.4 불변. 코드 중복, 이후 드리프트 |

## D-H1a-5 — 두 arm의 프롬프트 차이를 어떻게 격리하는가

**질문**: 두 arm의 차이를 "금지 조항 유무" **하나로** 격리하는 절차와 그
기계적 검증을 어떻게 정의하는가?

**왜 결정 사항인가**: 서문을 통째로 들어내는지 한 문장만 지우는지에 따라
프롬프트 길이·문맥·상대적 강조가 달라진다. 그러면 관측된 차이를 금지 조항에
귀속시킬 수 없다(교란).

**대상 텍스트는 두 문장이 한 문단에 붙어 있다**:

```
이 packet의 evidence item은 실행 전 provenance/eligibility 검증을
통과했다. 모델은 출처의 liveness나 우선순위를 재판정하지 않는다.
```

앞 문장("검증을 통과했다")까지 지우면 "검증이 끝났다"는 사실 자체가 사라져
**다른 변수가 함께 바뀐다.** 뒤 문장만 지울 것인지가 실질적 선택이다.

| 안 | 내용 | 검증 |
|---|---|---|
| **A** 뒤 문장 1개만 삭제 | 나머지 바이트 동일 | 두 프롬프트 diff가 그 문장 하나임을 테스트로 고정 |
| **B** 중립 문장으로 치환 | 길이 변화 최소화 | diff + 길이차 상한 단언 |
| **C** 각각 독립 작성 | 자연스러움 우선 | 검증 불가 — 교란 통제 포기 |

> **권고(비구속)**: A. 단 **"재판정하지 않는다" 문장만 삭제하고 "검증을
> 통과했다"는 남긴다.** 그리고 두 프롬프트 diff가 정확히 그 문장 하나임을
> 단언하는 테스트를 사전등록에 포함한다.

**미판정 시**: 관측된 차이를 금지 조항에 귀속시킬 수 없어 핵심 대조가 무의미해진다.

## D-H1a-7 — "독단 해결 = 사전지식 의존"이라는 해석을 어떻게 다루는가

**질문**: 이 인과 귀속을 유지하는가, 약화하는가, 검증 수단을 추가하는가?

**왜 결정 사항인가**: 이 귀속은 **검증 불가능한 단정**이다. 모델이 사전 지식이
아니라 **evidence 텍스트 내부의 신호**로 판단했을 가능성과 구분할 수단이 없다.
실제로 재료에 신호가 섞여 있다 — 문서 쪽엔 `주의: ...만 ...` 이라는 단정적
강조가 있고, 코드 쪽은 `source_kind: "test"`(통과 중인 테스트)로 제시된다.

| 안 | 내용 | 비용 |
|---|---|---|
| **A** 주장을 관측 수준으로 낮춤 | "독단 해결이 관측됐다"까지만 | 결론이 약해짐. 대신 방어 가능 |
| **B** 사후 프로빙 추가 | 모델에게 판단 근거를 되묻는 2단계 | 비용 증가 + 자기보고 신뢰도 문제 |
| **C** 신호 제거 fixture 변종 | 강조 어투·테스트 표시 제거 | **현행 하네스에서 실행 불가**(아래) |

**실측 제약**:
- **C는 불가능하다** — 하네스가 evidence 발췌를 원문과 **바이트 단위로 대조**하고
  불일치하면 생성을 거부한다. 원문을 변형한 fixture는 통과할 수 없다.
- B의 자기보고는 이 프로젝트가 명시적으로 신뢰도 **하**로 분류하는 근거 등급이다.

> **권고(비구속)**: A. C는 하네스가 거부하고, B는 프로젝트가 신뢰하지 않는 근거를
> 결론의 축으로 삼는다. 관측 수준으로 낮추면 결론은 약해지지만 방어 가능하고,
> 원인 분리는 후속 실험으로 넘기면 된다.

**미판정 시**: 실험은 돌아가지만 결론이 반증 가능한 형태로 서술되지 않는다.

   supersession을 모델에 **직접** 알려주는 형태가 되면 안 된다. (단 `source_kind`의
   `doc` vs `code` 구분은 **이미 허용된 필드**이므로 그 범위 안에서는 설계 가능하다.)
2. **동결 아티팩트(설계)와 운영 로그를 같은 커밋에 섞지 않는다.**
3. **E2.4 코호트는 현재 별도 인증 절차가 진행 중이다.** 그 표면(프롬프트 해시,

4. **agent 레지스트리는 세션 시작 시점에 고정된다.** 새 시험 대상 agent가

5. **fixture의 evidence는 원문과 바이트 일치해야 한다**(하네스가 강제).
