## 0. 한 줄 요약

Q8=B로 fixture는 이제 항목 **개수**로는 진짜 1-vs-1이다. 그런데 3차
독립 리뷰가, 개수와 무관하게 **두 증거의 문장 구조 자체가 비대칭**이라고
지적했다: code측 증거는 대안 해석을 명시적으로 반박하는 절을 담고 있고,
doc측 증거는 반박 없이 자기 주장만 한다. 운영 세션이 실측한 결과, 이
비대칭을 **개수를 늘리지 않고** 고치는 방법이 두 저장소 파일의 실제 구조상
막혀 있다는 것도 확인했다(§3). 이것이 바로 이 요청서가 존재하는 이유다 —
"고쳐라"가 아니라 "고칠 수 없는 이유가 있는데 이대로 진행해도 되는가"를
묻는다.

## 1. 사전 지식 없이 읽는 경우 (아는 내용이면 §2로)

### 1.1 실험

문서와 코드가 **같은 개념·속성 쌍**(`칼`의 `철`)에 대해 반대 type을 주장하는
실제 충돌 위에서, 계약문의 liveness 재판정 금지를 제거하면 모델의
**선택(select_type) / 보류(defer) 행동 분포**가 달라지는지 본다.
**정답 없음** — hidden oracle 없음, correctness 채점 없음(D-H1a-4).

| type | 뜻 |
|---|---|
| `essential_feature` | is-a 계층을 형성하는 분류적 본질 속성 |
| `structural_composition` | 부분-전체(has-a) 관계 |

### 1.2 지금 렌더되는 payload (Q5~Q8 전부 적용 후, verbatim)

```json
{
  "concept_feature_pair": {
    "concept": "칼",
    "feature": "철",
    "evidence_refs": ["ev1", "ev3"]
  },
  "evidence_items": [
    {
      "evidence_id": "ev1",
      "source_kind": "doc",
      "text": "(4) 재료-대상: 철은 칼의 재료 → essential_feature (재료는 본질이 될 수 있음)"
    },
    {
      "evidence_id": "ev3",
      "source_kind": "code",
      "text": "        \"(4) 재료-대상: 철은 칼의 재료 → structural_composition \"\n        \"(재료가 본질적이어도 관계는 has-a — 본질성은 별도 축)\\n\""
    }
  ]
}
```

`ev2`는 Q8=B로 이미 제거됐다 — 항목 수는 doc:1 / code:1로 진짜 1-vs-1이다.

## 3. Q9 (제기, 차단 아님) — 두 증거의 내용 구조가 비대칭이다

### 3.1 실측 — 무엇이 비대칭인가

| id | 원문 | 구조 |
|---|---|---|
| `ev1` (doc) | `...→ essential_feature (재료는 본질이 될 수 있음)` | **지지만 함** — "재료는 본질이 될 수 있다"는 자기 주장의 근거를 댈 뿐, 반대 해석(has-a로 볼 수도 있다는 것)을 언급하거나 반박하지 않는다 |
| `ev3` (code) | `...→ structural_composition (재료가 본질적이어도 관계는 has-a — 본질성은 별도 축)` | **반박까지 함** — "재료가 본질적이어도"라는 양보절로 대안 해석의 존재를 인정한 뒤, "관계는 has-a"로 반박하고 "본질성은 별도 축"이라는 일반 원리까지 덧붙인다 |

code측 문장은 doc측이 말할 수 있는 것(재료는 본질적일 수 있다)을 **먼저
인정한 뒤 논파하는 구조**다. 이것은 `source_kind`나 항목 개수와 무관한
**세 번째 축의 비대칭**이며, code측에 "최후 발언"처럼 읽힐 위험이 있다.

### 3.2 실측 — 왜 개수를 안 늘리고는 못 고치는가

두 소스 파일 전체에서 `철`·`칼`을 검색하면 이 두 인용 지점이 **유일한
등장**이다:

```
$ grep -n "철\|칼" docs/phase_a_implementation_packet.md
102:(4) 재료-대상: 철은 칼의 재료 → essential_feature (재료는 본질이 될 수 있음)

$ grep -n "철\|칼" conceptgate/concept_gate_v7.py
1192:        "(4) 재료-대상: 철은 칼의 재료 → structural_composition "
```

즉 **이 개념/속성 쌍에 대해 두 파일이 실제로 말하는 문장은 이것뿐**이다.
doc측에 반박 문장을 "추가"하려면 새 문장을 지어내야 하는데, evidence
text는 실제 파일 줄에서 발췌한 것이어야 한다(`_h1a_surface.py::_excerpt_matches`
가 `start_line:end_line` 발췌를 원문과 바이트 대조한다 — 지어낸 문장은
통과하지 못한다).

**유일한 실제 확장 지점은 바로 옆줄이다**(doc측 106번째 줄):

```
102: (4) 재료-대상: 철은 칼의 재료 → essential_feature (재료는 본질이 될 수 있음)
103: (5) 단계-과정: 유충은 변태의 단계 → contextual_usage
104: (6) 장소-영역: 오아시스는 사막의 부분 → locational
105:
106: 주의: 재료-대상(4)만 essential_feature가 될 수 있습니다.
```

이 `주의:` 문장(구 `ev2`)이 사실 doc측의 "반박형" 문장에 가장 가깝다 —
"(4)만" essential_feature라는 **배타성 단언**이다. 그런데 `source_ref.kind
== "file_lines"`는 **연속 구간만** 발췌할 수 있어(줄을 건너뛸 수 없다),
102번째 줄과 106번째 줄만 골라 담을 수 없다. 102-106 전체를 담으면
103·104번째 줄의 `contextual_usage`·`locational`(H1a의 `selected_type`
enum **밖** type)이 함께 노출된다 — **Q8.1이 code측에 대해 이미 금지한
것과 정확히 같은 문제**가 doc측에도 대칭으로 존재한다.

code측도 대칭이다. `ev3`의 반박절을 **제거**해 doc측과 구조를 맞추려면
`end_line`을 1192로 줄여야 하는데:

```python
# 실측: end_line=1192만 취하면
"        \"(4) 재료-대상: 철은 칼의 재료 → structural_composition \""
```

문장이 마침표 없이 끝나고("→ structural_composition " + 닫는 따옴표),
이는 원문을 "다듬어" 실제보다 약하게 만드는 것이다 — 반박절이 실제로
존재하는데 그것을 빼고 인용하는 것은 code측 논거를 인위적으로 약화시키는
행위이지, 대칭을 만드는 중립적 행위가 아니다.

### 3.3 왜 운영 세션이 정하지 않는가

세 선택지 전부 실험이 무엇을 측정하는지에 영향을 준다:

| 안 | 내용 | 위험/근거 |
|---|---|---|
| **A** | 그대로 두고 사전등록에 **한계로만 명시**(L1·L2와 같은 자리에 L3 추가) | 최소 변경. 단 code측에 "최후 발언" 구조가 있다는 것을 인정한 채 진행 — arm 대비 자체는 오염시키지 않지만(양 arm에 동일), **절대 select_type 비율이 code측으로 쏠릴 수 있고 이는 이 실험이 애초에 보고하지 않는 값(P3 참조)이라 실질적 위험은 낮다** |
| **B** | doc측 인용 구간을 102-106으로 넓혀 **양쪽 다** enum 밖 이름을 노출(code측도 대칭으로 전체 6-패턴 문단 인용) | 대칭 확보. 단 Q8.1이 이미 "이 fixture에서는 금지"라고 못박았다 — 그 판정을 재론하는 것이 됨. 판정 범위를 넘는지 이 문서가 되묻는다 |
| **C** | `ev3`의 `end_line`을 1192로 줄여 반박절 제거 | code측 논거를 실제보다 약하게 인용하는 것 — §3.2가 보이듯 원문을 다듬는 행위이며, "저장소가 실제로 강제하는 상태를 정직하게 기록한다"는 fixture의 기존 원칙(builder_metadata.recorded_type_rationale)과 정면 충돌 |
| **D** | 이 개념/속성 쌍을 **포기**하고 두 소스 파일 전체에서 구조적으로 더 대칭적인 다른 1-vs-1 쌍을 새로 찾는다 | 가장 큰 변경. trial 0건이라 재동결 비용은 없으나(Q5·Q6·Q8 전부 같은 이유로 fixture를 고쳤다), 대칭적인 실제 doc/code 쌍이 저장소에 존재하는지 자체가 미지수 — 탐색 비용 발생 |
| **E** | 그 밖 | |

**부수 질문(B 또는 D를 고려할 때)**: 이 실험은 이미 `evidence-reading rule`
자체가 "select 쪽에만 작용하고 defer는 잔여값"이라는 비대칭을 L1로
선언하고 진행 중이다(`H1A_ISSUE_REGISTER.md` §E). 이번 것도 같은 성격의
"완전히 제거할 수 없는 비대칭"이라면, **L1·L2와 같은 급으로 선언하고
진행(A)하는 것이 이 프로젝트의 기존 판정 패턴과 일관되는가**, 아니면
Q8이 개수 비대칭을 반드시 고치라고 했던 것처럼 이번에도 반드시 고쳐야
하는 차이가 있는가?

## 4. 넘을 수 없는 제약 (Q5~Q8과 동일, 재확인)

1. 모델 대면 필드는 `concept_feature_pair`(concept/feature/evidence_refs,
   type 없음) + `evidence_items[].{evidence_id, source_kind, text}` 뿐
2. evidence text는 **실제 파일에서 발췌한 바이트**여야 한다 — 지어낸
   문장·다듬은 문장 불가(§3.2·§3.3 C안 참고)
3. **Q8.1 유지**: 이 fixture에서 enum 밖 type 이름(`contextual_usage`,
   `locational` 등) 노출 금지 — B안을 택하면 이 제약을 재판정해야 한다
4. hidden correctness oracle 없음(D-H1a-4)
5. **실행된 trial 0건.** 이 조건은 첫 trial과 함께 사라진다
