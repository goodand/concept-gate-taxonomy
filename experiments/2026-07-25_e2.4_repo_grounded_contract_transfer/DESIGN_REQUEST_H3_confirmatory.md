## 0. 한 줄 요약 — deferred 5항목보다 앞선 문제가 있다

D-H3-5는 확증 규모를 정하려면 SESOI·다중성 제어·alpha/power·독립 held-out
fixture 수 K·분석 모형이 필요하다고 했다. **이 다섯은 전부 표집틀(sampling
frame)을 전제한다.** 그런데 실측 결과 이 저장소에는 표집틀이 없다 — 세
fixture는 표집된 것이 아니라 의도대로 동작할 때까지 **제작**됐고, 그 재료
공급이 class별로 극단적으로 비대칭이다(M2~M6).

따라서 요청하는 판정은 "K를 몇으로 할까"가 아니라 **"이 재료로 정의 가능한
estimand는 무엇인가"**다.

## 1. 이 실험이 무엇인가 (사전 지식 없이 읽는 경우)

이 절만 읽으면 이후 전체를 판정할 수 있다. 이미 아는 내용이면 §3(실측)으로 건너뛰어라.

### 1.1 프로젝트

ConceptGate는 자연어에서 개념(concept)과 그 속성(feature)을 뽑아 온톨로지
계층을 만드는 시스템이다. 원칙은 **"LLM이 제안하고, 결정론이 판정한다."**
각 feature에는 6개 중 하나의 **type**이 붙는다:

| type | 뜻 |
|---|---|
| `essential_feature` | is-a 계층을 형성하는 분류적 본질 속성 |
| `contextual_usage` | 맥락에 따라 달라지는 용법 |
| `locational` | 장소·영역 관계 |
| `functional` | UFO 의미의 기능적 역할 |
| `social_treatment` | 사회적·법적 처우 |
| `structural_composition` | 부분-전체(has-a) 관계 |

이 6개는 **전문 용어**이며 일상어와 다르다(`functional` ≠ "기능이 있다",
`structural_composition` ≠ "구조를 가진 코드").

### 1.2 E2.4가 묻는 것

클라이언트 LLM 에이전트에게 **evidence packet**을 준다. packet은 세 부분이다:

- `candidate_concepts` — 판정 대상. 각 concept의 feature와 **현재 붙어 있는
  type**
- `evidence_items` — 근거 텍스트. 각 항목은 `evidence_id`/`source_kind`/`text`
  **3개 필드뿐**(경로·주석·메타데이터 없음. 오라클 유출을 구조적으로 차단)
- `server_response` — 결정론적 파이프라인의 출력(status 등)

에이전트는 이 packet **만** 보고 하나의 행동을 고른다. 외부 지식 사용 금지.

**질문**: 구조화된 계약(evidence audit → 충분성 판정 → 불변식 확인 → 행동)을
강제하면, 근거가 불충분할 때 **함부로 단정하지 않고 보류**하는가?

### 1.3 세 arm

세 arm은 **동일한 packet 바이트**를 받는다. 차이는 프롬프트 규칙과 응답
스키마뿐이다.

| arm | 프롬프트 규칙 | 응답 스키마 |
|---|---|---|
| `CONTROL_REPO_H3` | 6개 type 어휘 설명만 | 공통 4필드 |
| `A_REPO_H3` | 위 + **전역 일관성 규칙**("같은 feature 이름이 여러 concept에 있으면 하나의 type으로 통일하라" — 선행 실험 E2.2.3에서 단독으로 효과가 확인된 규칙) | 공통 4필드 |
| `CONTRACT_REPO_H3` | 위와 다른 계열 — **7개 절의 계약문**: packet 외 지식 금지 / 행동 전 evidence audit 필수 / 충분성 5단계 절차 / 전역 불변식 / repair 조건 / 보류 조건 / 수용 조건 | 공통 4필드 **+ `contract_assessment`**(감사 내역·충분성 판정·불변식 점검을 구조적으로 강제) |

계약의 핵심 규칙 하나가 이 문서 전체를 지배한다:

> **"코드가 무엇을 하는지"를 서술하는 텍스트는, 그 자체로는 6개 type 중
> 어느 것에 대해서도 근거가 되지 않는다.** 근거가 되려면 텍스트가 그
> feature의 **온톨로지적 성격**(분류적 본질인가 / 부분-전체인가 / 역할인가…)을
> **명시적으로 서술**해야 한다.

이 규칙 때문에 임의의 구현 코드는 자동으로 "근거 불충분"이 된다. 이것이
§4의 공급 비대칭을 낳는다.

### 1.4 공통 행동 어휘

선행 판정(D-H3-1)이 세 arm에 동일한 행동 어휘를 부여했다. 이전에는 legacy
arm이 `report_done`/`repair`/`request_evidence`를, 계약 arm이
`accept_report`/`repair`/`abstain`을 써서 **보류를 표현할 수 있는 arm과 없는
arm이 갈렸고**, 그러면 "보류가 관측되지 않음"이 *판단하지 않았다*인지
*표현할 수 없었다*인지 분해되지 않는다. 그래서 셋 다:

| action | 뜻 |
|---|---|
| `accept_report` | 현 상태가 안전하며 조치 불요 |
| `repair` | 근거 있는 수정이 필요 |
| `defer` | 이 packet만으로 확정 불가, 보류 |

`contract_verdict`(계약 arm 내부 진단)는 **1차 지표가 아니다**(D-H3-3).

### 1.5 semantic class (숨은 정답)

각 fixture에는 사람이 붙인 정답 class가 있고 **모델에게는 절대 노출되지
않는다**. class → 기대 행동:

| class | 뜻 | 기대 action |
|---|---|---|
| `sufficient_consistent` | 근거가 현재 type을 충분히 지지 → 고칠 것 없음 | `accept_report` |
| `sufficient_repairable` | 근거가 **다른** type을 명시 → 고칠 수 있음 | `repair` |
| `insufficient` | 어떤 type도 명시적으로 지지되지 않음 | `defer` |
| `conflicting` | 동등 강도로 상충하는 근거 | (미확보 종결, M11) |

### 1.6 용어

- **fixture** — 하나의 packet을 만들기 위한 제작용 파일. 숨은 정답과 출처
  메타데이터를 포함하며, 모델에게는 화이트리스트 빌더가 걸러낸 3필드만 간다
- **trial** — 한 arm × 한 fixture × 1회 모델 호출
- **R** — 같은 fixture·arm의 반복 호출 수 (여기서는 5)
- **K** — 독립 fixture 수 (class당, 여기서는 1)
- **held-out** — 모델 결과와 **무관하게** 선정된, 확증용 별도 fixture
- **비인증(non-certifying)** — 통과/실패 판정이나 우월성 주장을 산출하지
  않는 실행

### 3.1 문제의 7문장 — 전문 (D-H3C-3 판정에 필요)

저장소 전체를 통틀어 존재하는 온톨로지 관계 서술의 **전부**다. 독립성을
판정하려면 서술이 아니라 원문을 봐야 하므로 그대로 옮긴다.

**템플릿 ① `{X}의 {Y}는 {X} 몸체의 구성 부분이다`** → `structural_composition`

1. `돌체의 바퀴는 돌체 몸체의 구성 부분이다`  ← **E2.4가 소비**(sufficient_repairable)
2. `카페린의 손잡이는 카페린 몸체의 구성 부분이다`  ← **E2.4가 소비**(sufficient_consistent)
3. `엔진박스의 구동축은 엔진박스 몸체의 구성 부분이다`
4. `엔진박스의 냉각판은 엔진박스 몸체의 구성 부분이다`
5. `차체프레임의 고정핀은 차체프레임 몸체의 구성 부분이다`

**템플릿 ② `{X}에서 {Y}는 {Z} 기능을 제공한다`** → `functional`

6. `돌체린에서 바퀴는 이동 기능을 제공한다`
7. `카페토에서 손잡이는 운반 기능을 제공한다`

미사용 잔여는 3·4·5·6·7의 **5개**다. 3과 4는 **같은 X(엔진박스)** 의 서로
다른 부품이고, 1·2·3·4·5는 명사 두 개를 뺀 나머지가 **문자 단위로 동일**하다.

### 3.2 pilot 전체 분포 (45 trial) — D-H3C-4 판정에 필요

분모는 **전체 n**이다. schema-invalid는 어떤 action으로도 세지 않고
action-incorrect로 처리한다(선행 판정 §4 요구).

| class (기대 action) | arm | n | invalid | accept_report | repair | defer |
|---|---|---|---|---|---|---|
| **insufficient** (→defer) | CONTROL | 5 | 0 | 0 | **5** | 0 |
| | A | 5 | 1 | **4** | 0 | 0 |
| | CONTRACT | 5 | 1 | 0 | 0 | **4** |
| **sufficient_consistent** (→accept_report) | CONTROL | 5 | 0 | 2 | 0 | **3** |
| | A | 5 | 1 | 0 | 0 | **4** |
| | CONTRACT | 5 | 2 | **3** | 0 | 0 |
| **sufficient_repairable** (→repair) | CONTROL | 5 | 0 | 0 | **5** | 0 |
| | A | 5 | 0 | 0 | **5** | 0 |
| | CONTRACT | 5 | 0 | 0 | **5** | 0 |

파생 지표:

| 지표 | CONTROL | A | CONTRACT |
|---|---|---|---|
| P(defer \| insufficient) — **1차** | 0.00 | 0.00 | **0.80** |
| false-defer @ sufficient_consistent | 0.60 | 0.80 | **0.00** |
| false-defer @ sufficient_repairable | 0.00 | 0.00 | 0.00 |
| macro action accuracy (3 class 평균) | 0.47 | 0.33 | **0.80** |
| invalid-output rate | 0.00 | 0.13 | **0.20** |
| 내부 action/`contract_verdict` 일치 | — | — | 12/12 |

**이 표에서 육안으로 보이는 것 3가지**(판정 대상이지 결론이 아니다):

1. `sufficient_repairable` 행은 **세 arm이 완전히 동일**하다(5/5 repair).
   이 class는 arm을 구별하지 못한다 — 즉 3 class 중 실제로 정보를 주는 것은
   2개다.
2. CONTROL은 `insufficient`에서 **5/5 repair**했다. 보류하지 않은 게 아니라
   **근거 없이 고쳤다.** A는 같은 자리에서 4/5 `accept_report`했다 — 역시
   보류하지 않았으나 CONTROL과 **다른 방향**으로 틀렸다.
3. 두 비교 arm의 오류는 `sufficient_consistent`에서 **defer 쪽으로** 쏠린다
   (0.60, 0.80). 즉 세 arm은 "보류의 양"이 아니라 **"보류의 위치"**가 다르다.

## 4. 실측에서 따라 나오는 구조

**공급 비대칭.** `insufficient` class 재료는 사실상 무제한이다(임의의 구현
코드는 온톨로지적 성격을 서술하지 않으므로 자동으로 insufficient다). 반면 두
`sufficient` class는 **남은 5문장, 템플릿 2개, 전부 합성**이 전부다(M2~M6).

**"repo-derived"의 의미가 class마다 다르다.** `insufficient`는 실제
저장소에서 왔고, 두 `sufficient`는 이 프로젝트가 이전 실험을 위해 작성한
합성 문장에서 왔다(M1). 같은 실험 안에서 두 종류의 "repo-derived"가 섞여
있다.

**M10의 양면성.** 라벨이 기계적으로 결정된다는 것은 좋은 소식처럼 보이지만,
그 결정가능성은 **재료가 두 템플릿으로 쓰였다는 사실에서 나온다.** 규칙
("텍스트가 feature의 온톨로지적 성격을 명시적으로 서술하는가")이 일반적으로
결정 가능하다는 증거가 아니다 — 오히려 M7이 반대를 보여준다: 실제 산문에
같은 규칙을 적용하려 한 4번의 시도가 전부 독립 리뷰에서 기각됐고, 그
기각들은 서로 다른 이유였다(순환성, 절차성, 생사, 자기인용). 규칙의 적용이
사례마다 논쟁됐다는 뜻이다.

## 5. 판정 요청 항목

각 항목은 **질문 → 왜 판정 사항인가 → 선택지 → 실측 제약 → 권고(비구속) →
미판정 시 귀결** 순이다.

---

### D-H3C-1 (최우선) — Δ의 확률 공간은 무엇인가

**질문.** `Δ = P(defer | insufficient, CONTRACT) − P(defer | insufficient, 비교 arm)`
에서 이 확률은 무엇에 대한 확률인가?

**왜 판정 사항인가.** K=1(class당 packet 1개), R=5인 현재 설계에서 유일한
확률원은 모델의 샘플링 랜덤성이다. 그러면 Δ는 "이 특정 packet에서 이 모델이
얼마나 자주 defer하는가"를 재며, R을 늘리면 그 추정치가 정밀해질 뿐
일반화되지 않는다. "insufficient packet 일반"으로 가려면 packet들의 모집단과
그로부터의 표집 절차가 있어야 하는데, M1~M7은 packet이 표집된 적이 없고
**제작**됐음을 보인다. D-H3-5가 남긴 SESOI·다중성·power는 **전부 이 표집틀을
전제**하므로, 이 항목이 그 다섯보다 앞선다.

**선택지.**

| 안 | 내용 | 대가 |
|---|---|---|
| A | 확률 공간을 **모델 샘플링만**으로 확정. estimand는 packet-조건부. K는 설계 변수에서 제외 | class 수준 주장을 영구히 포기. 결론은 항상 "이 packet에서" |
| B | packet 모집단을 **생성 절차로 정의**(템플릿 + 명사 치환 규칙을 사전등록하고 그로부터 표집) | 모집단이 "이 프로젝트가 만든 템플릿의 인스턴스"가 됨. 외적 타당도가 템플릿에 갇힘 |
| C | 모집단을 **실제 저장소 산문**으로 정의하고 거기서 표집 | M6에 따르면 표본 공간이 공집합. 실행 불가 |
| D | estimand를 **행동 대비**가 아닌 다른 것으로 재정의(예: 동일 packet에 대한 arm 간 응답 분포의 거리) | 원래 질문("계약이 불충분을 더 잘 잡아내는가")과 달라짐 |

**실측 제약.** C는 M6(실 산문 히트 0)와 M7(실 산문 기반 4회 시도 전부 기각)에
의해 배제된다고 본다. B는 M3(템플릿 2개)에 의해 모집단이 매우 좁다.

**권고 — 비구속, 앵커링 주의.** A가 현재 재료와 정합적이라고 본다. 다만 이는
"확증 실험을 하지 않는다"와 사실상 같으므로, 그 귀결을 받아들일지가 판정
사항이다.

**미판정 시 귀결.** SESOI·power 계산을 시작할 수 없다. 계산을 강행하면
정의되지 않은 모집단에 대한 신뢰구간을 보고하게 된다.

---

### D-H3C-2 — 존재 주장인가 전칭 주장인가

**질문.** H3가 licensed하는 결론 형식은 다음 중 무엇인가?

- **존재**: "계약 인터페이스가 보류 행동을 바꾸는 repo-derived packet이
  존재한다."
- **전칭**: "insufficient class 일반에서 계약 인터페이스가 더 자주 보류한다."

**왜 판정 사항인가.** M8(Δ=+0.80, specificity 유지)은 존재 주장을 이미
지지한다. 전칭 주장은 D-H3C-1이 A로 판정되면 원리적으로 도달 불가, B로
판정되면 "템플릿 인스턴스 일반"이라는 축소된 전칭이 된다. 어느 쪽을 목표로
하느냐가 이후 모든 설계를 결정한다.

**선택지.** ①존재 주장으로 확정하고 E2.4를 종료 ②축소된 전칭(템플릿 모집단)
③전칭을 목표로 유지하되 재료 확보를 별도 과제로 분리 ④H3의 질문 자체를 재구성

**권고 — 비구속.** ①이 현 데이터에 정직하다고 본다. 다만 프로젝트가 원래
답하려던 질문이 전칭이었다면 ③도 합리적이다 — 단 그 경우 "재료 확보"가
새 실험 하나 규모임을 명시해야 한다(M7: 1개 fixture에 5차 시도).

**미판정 시 귀결.** pilot 결과가 논문·보고서에서 전칭으로 읽힐 위험. 현재
코드는 이를 기계적으로 막고 있으나(`h3_pilot_score.json`이
`certifying: false`, 테스트가 "certified" 문자열 출현을 실패시킴) 서술 층에는
그런 가드가 없다.

### D-H3C-3 — 템플릿 인스턴스는 독립 표본인가

**질문.** 남은 5문장(M5)으로 held-out fixture를 만들면 K=5인가, K=2(템플릿
수)인가, K=1(단일 저자·단일 생성 절차)인가?

**왜 판정 사항인가.** D-H3-5는 "반복 시행 수 R과 독립 fixture 수 K를
표본수에서 분리하라"고 명시했다. 그 분리를 적용하면, 같은 템플릿에 명사만
바꾼 문장들이 서로 독립인지가 곧바로 문제가 된다. 독립이 아니라면 계층
모형의 클러스터 단위는 fixture가 아니라 템플릿이며, 유효 표본수는 5가 아니라
2 이하다.

**선택지.** ①K=5(문장 단위) ②K=2(템플릿 단위, 문장은 템플릿 내 반복)
③K=1(전부 하나의 생성 절차) ④독립성을 경험적으로 추정(템플릿 간 분산 대
템플릿 내 분산)

**실측 제약.** M3에 따르면 템플릿 ①이 5문장, 템플릿 ②가 2문장이다. 템플릿
①의 5문장은 `{X}의 {Y}는 {X} 몸체의 구성 부분이다`에서 X·Y만 다르다.
④를 하려면 템플릿당 복수 인스턴스가 필요한데 템플릿 ②는 2개뿐이다.

**권고 — 비구속.** ②가 보수적이라고 본다. 그러나 K=2로는 어떤 class 수준
추론도 뒷받침되지 않으므로, 실질적으로 D-H3C-1 A와 같은 결론에 도달한다.

**미판정 시 귀결.** K를 5로 세면 유효 표본수를 2.5배 과대평가한다.

### D-H3C-4 — 3×3 결과 구조를 단일 Δ로 축약하는 것이 정당한가

**질문.** 결과는 arm마다 (3 class × 3 action) 혼동 구조인데 1차 지표는
그중 한 칸의 대비(P(defer|insufficient))뿐이다. M9의 역전을 본 뒤에도 이
축약이 옳은가?

**왜 판정 사항인가.** M9에 따르면 비교 arm들은 `insufficient`에서 defer하지
않으면서 `sufficient_consistent`에서는 대량 defer한다(CONTROL 3/5, A 4/5).
즉 arm 간 차이는 "보류의 양"이 아니라 **"보류의 위치"**다. 단일 Δ는 이
구조를 못 담고, 극단적으로는 두 arm이 같은 Δ를 내면서 정반대 오류 패턴을
가질 수 있다. 사전등록된 estimand가 잘못 고른 요약통계일 가능성.

**선택지.** ①현행 Δ 유지, 역전은 2차 지표로 보고 ②1차 지표를 macro action
accuracy로 교체 ③1차 지표를 혼동행렬 전체의 거리(예: arm 간 행동 분포
divergence)로 교체 ④defer의 **조건부 적절성**(defer한 경우 중 실제
insufficient였던 비율 = precision)과 recall을 쌍으로 보고

**실측 제약.** 사전등록 변경이므로, 이미 결과를 본 상태에서의 변경은 pilot
데이터에 소급 적용할 수 없다(D-H3-5: "pilot 결과로 판정 규칙을 바꾸면 그
cohort는 새 실험으로 동결"). 즉 이 판정은 **다음 실행부터** 적용된다.

**권고 — 비구속.** ④가 M9를 가장 정직하게 담는다고 본다. 다만 ①을 유지하고
역전을 별도 발견으로 보고하는 것도 방어 가능하다 — 결과를 본 뒤 지표를
바꾸는 것 자체가 자유도이기 때문이다.

**미판정 시 귀결.** Δ=+0.80이 "CONTRACT가 더 잘 판단한다"로 읽히지만, 실제
데이터는 "세 arm이 서로 다른 위치에서 틀린다"에 가깝다.

### D-H3C-5 — invalid-output의 인과적 지위

**질문.** CONTRACT의 schema-invalid 비율이 0.20, CONTROL은 0.00이다(M8).
invalid를 treatment 효과의 일부로 볼 것인가, 매개변수로 볼 것인가, 교란으로
볼 것인가?

**왜 판정 사항인가.** 판정문 §4는 invalid를 action-incorrect로 처리하도록
요구했고 그렇게 구현했다. 그런데 CONTRACT의 invalid가 높은 이유는 스키마가
더 크기 때문(`contract_assessment` 추가)이고, 스키마 크기는 treatment의
일부다. 따라서 현재 Δ는 "계약이 더 잘 보류한다"와 "계약이 더 자주 출력을
깨뜨린다"가 **상쇄된 값**이다. 두 기전을 분리할지가 판정 사항.

**선택지.** ①treatment의 일부로 확정(현행) ②매개변수로 보고 mediation
분석 ③invalid를 별도 결과로 보고하고 Δ는 valid-only로도 병기(단
판정문 §4와 충돌) ④스키마 부담을 arm 간 동등화(모든 arm에 동일 크기 진단
필드 요구)해 교란 제거

**실측 제약.** ④는 arm 간 허용 차이를 "등록된 계약 텍스트와 진단 schema
차이뿐"으로 한정한 new_constraints와 긴장한다 — 진단 schema 차이가 곧
treatment이기 때문이다.

**권고 — 비구속.** ①유지 + invalid rate 필수 병기(현행)가 판정문과 정합적.
다만 Δ가 상쇄값이라는 사실은 결과 서술에 명시돼야 한다.

**미판정 시 귀결.** Δ가 과소추정된 채 보고되고, 그 방향이 실험 대상 arm에
불리하다는 점이 드러나지 않는다.

---

### D-H3C-6 — 규칙 따르기: 라벨의 결정가능성은 어디서 오는가

**질문.** M10은 class 라벨이 정규식으로 3/3 재현되고 실 산문 false positive가
0임을 보인다. 이것을 "라벨링은 기계화 가능하다"의 근거로 쓸 수 있는가?

**왜 판정 사항인가.** 검출기가 성공한 이유는 재료가 두 템플릿으로 쓰였기
때문이다(M3). 같은 규칙을 실제 산문에 적용하려던 4번의 시도는 전부 독립
리뷰에서, **서로 다른 이유로** 기각됐다(M7). 즉 규칙의 외연이 사례마다
논쟁됐다. 그렇다면 M10은 규칙의 결정가능성이 아니라 **코퍼스의 템플릿성**을
측정한 것이며, 이를 근거로 held-out 라벨을 기계적으로 붙이면 "독립적
라벨링"이 실은 "같은 템플릿의 재인식"이 된다.

**선택지.** ①M10을 기계화 근거로 채택 ②M10을 템플릿성 측정으로 해석하고
라벨링은 인간·독립 판단으로 유지(그 경우 판단자 신뢰도 확립 절차 필요:
사전등록 코딩 규칙 + 복수 판정자 + 일치도) ③규칙 자체를 결정 가능하게
재작성(무엇이 "온톨로지적 성격의 명시적 서술"인지 형식 기준으로) ④라벨을
포기하고 오라클 없는 서술적 설계로 전환(H1a가 택한 길)

**권고 — 비구속.** ②가 정직하다고 본다. ③은 매력적이지만, 4번의 기각 이유가
서로 달랐다는 사실(M7)은 형식화가 쉽지 않음을 시사한다.

**미판정 시 귀결.** held-out fixture를 만들면서 그 라벨의 독립성을 근거 없이
가정하게 된다 — D-H3-6이 막으려던 결과 의존적 선택이 형태만 바꿔 재발한다.
