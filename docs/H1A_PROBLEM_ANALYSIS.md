## 1. 패턴 — 문제 정의

같은 형태가 반복됐다. 개별 이슈보다 이쪽이 재사용 가치가 있다.

### P1. 가드가 **참인 명제**를 검사하는데, 그것이 **필요한 명제가 아니다**

**정의**: 검사기가 정직하게 통과하고 그 판정도 옳지만, 그것이 참으로
만드는 명제와 실제로 보증되어야 할 명제가 다르다. recall/precision을 아무리
재도 잡히지 않는다 — 두 측정 모두 "가드가 올바른 것을 검사한다"를 전제하기
때문이다.

이 실험에서 **여섯 번** 발생했다:

| # | 가드가 참으로 만든 것 | 필요했던 것 | 결과 |
|---|---|---|---|
| 1 | "두 프롬프트의 diff가 지정된 한 문장이다" | "어느 arm에도 동등한 금지가 남지 않았다" | 조작 무효(blocker #16) |
| 2 | "두 anchor 변종이 서로 같다" | "각 변종이 **원본 fixture와** 같다" | 대칭 오염이 통과 |
| 3 | "절의 바이트가 정확히 이동했다" | "옮겨진 자리에서도 **같은 것을 가리킨다**" | 선행사 상실(Q5) |
| 4 | 스키마 `description`이 오라클 금지를 **선언** | 그 선언을 **실행**하는 검사기 | fixture 4개가 몇 주간 유출(E2.4 선례) |
| 5 | "잔여-금지 tripwire 목록에 이 어구가 없다" | "이 **의미**의 금지 문장이 어떤 어구로도 없다" | 3차 리뷰가 의역 3종으로 재현 — `RESIDUAL_TRIPWIRES_EN`은 **닫힌 열거**라 원리상 완전 봉쇄 불가 |
| 6 | "이 문자열이 허용 type 값과 **정확히 같지 않다**" | "이 문자열이 허용 type 값을 **부분으로도 담지 않는다**" | 산문에 박힌 type 이름이 무비용 정답 경로로 통과(3차 리뷰) |

**#3·#5·#6이 새 변종이다.** 바이트 동일성 검사(#3)는 **문맥 의존 의미**에
대해 원리상 아무 말도 못 한다. 닫힌 어구 열거(#5)는 **생각해본 표현만**
잡는다 — 완전 봉쇄가 구조적으로 불가능하다는 것을 코드 주석에 명시했다.
정확 일치(#6)는 **부분 노출**을 놓친다. 셋 다 "가드가 통과 = 위험 부재"가
아니라 "가드가 통과 = **이 특정 검사 방식이 잡을 수 있는 범위 안엔 없음**"
으로 읽어야 한다는 하나의 결론으로 수렴한다.

### P2. 계측기의 **침묵이 검증되지 않았다**

**정의**: 가드가 통과했는데, 그 가드가 애초에 **실패할 수 있음을 보인 적이
없다.** 침묵은 그것이 말할 수 있음을 보인 뒤에만 의미가 있다.

| 사례 | 실태 |
|---|---|
| 잔여-금지 가드 | 한국어 tripwire 8종만. Q3=B로 template이 **영어가 된 뒤에도** 그대로였다가(F7로 해소), 3차 리뷰가 **의역**에서 다시 침묵을 재현 |
| 진단 evidence 불변 검사 | 뮤테이션 4종 중 1종(대칭 오염)이 **누출** |
| 코더 교정 코퍼스 | 18/18 통과 — 단 그것만으로는 "코퍼스가 아무것도 구별 못 함"과 구별 불가 → 뮤테이션 3종 주입으로 해소 |
| no-anchor 가드(신규) | Q6=A 직후엔 뮤테이션(답 담는 키·bare 값 주입)만으로 확인 — 3차 리뷰가 **산문에 박힌 값**이라는 세 번째 주입 형태로 침묵을 재현 |

### P3. **상위 판정을 충실히 따른 것이 새 결함을 만든다**

**정의**: 구속력 있는 판정을 정확히 이행했는데, 제거된 것이 **다른 것을
떠받치고 있었다.** 판정 자체는 옳고, 이행도 옳고, 그래도 결함이 생긴다.

| 판정 | 이행 | 파생 결함 |
|---|---|---|
| Q3=B "E2.4 서문을 버려라" | 버림 | `그 판정은 이미 끝났고…`의 선행사가 그 서문에 있었다 → **Q5** |
| Q3=B "규칙 2~7을 버려라" | 버림 | 규칙 3의 동률 조항이 유일한 충돌 처리 규칙이었다 → 대체 없이 **공백** → **Q7** |

**이 패턴은 판정을 의심하라는 뜻이 아니다.** 판정 이행 후 "**제거한 것이
무엇을 떠받치고 있었는가**"를 별도로 확인하라는 뜻이다. Q5·Q7 모두 이제
**적용 완료**다(§2.1).

### P4. **문서가 자기 상태를 잘못 서술한다**

**정의**: 아티팩트의 자기서술이 그 아티팩트의 실제 속성과 다르다. 자기서술은
검증되지 않으므로 조용히 stale해진다.

| 아티팩트 | 주장 | 실제 |
|---|---|---|
| `builder_metadata.no_oracle` | "Neither type is marked right." | payload가 두 허용값 중 하나를 건넨다(Q6 적용 전) |
| `builder_metadata.purpose` | "This is a 1-vs-1 conflict" | 모델이 보는 것은 doc 2 대 code 1(Q8 적용 전) |
| `h1a_schema.json` description | 조작 = "one prohibition sentence"(D-H1a-5=A) | Q1=B와 Q3=B가 두 번 뒤집음 |
| `EXPERIMENT_METHODOLOGY.md` | "concept-gate-e2.*-wt worktree 전부 포함" | 그 worktree들에서 **열 수 없었다** |
| `PREREGISTRATION.md`의 동결된 null 보고 문장(신규) | "fixed anchor... the anchor diagnostic did not detect..." | Q6=A가 앵커와 그 진단 **둘 다 은퇴**시킨 뒤에도 그대로 남아 있었다(3차 리뷰 minor) |
| (E2.4 선례) `cg_partwhole.py` docstring | "참조용 — 직접 import하지 않음" | 두 모듈이 라이브 경로에서 import |

### P5. **검색 방법이 결론의 완전성을 결정한다**

**정의**: lexical 검색은 "이것이 **이미 결정됐는가**"에 답할 수 없다. 결정
문서의 제목이 질문의 어휘를 포함하지 않을 수 있기 때문이다.

실측: 활성 실험 폴더 정리를 설계하면서 `rg`로 "디렉토리 정리 / DESIGN_DECISION
/ canonical"을 훑었다. 이미 채택된 결정
(`notes/audits/vault/symlink-vs-moc-2026-07-30.md`, `status: finished`)이
**걸리지 않았다** — 그 문서 제목이 "Format storage, symlink views, and MOC
validation"이라 교집합이 0이기 때문이다. **backlink 1홉**으로 나왔다.

### P8. **문서를 찾아도, 근거 문장을 문맥 없이 인용하면 범위를 잘못 읽는다**(신규)

**정의**: P5가 "찾기 자체"의 실패라면, 이것은 **찾은 뒤**의 실패다.
`grep`이나 backlink로 정확한 원본 문서에 도달해도, 그 문서의 핵심 근거
문장 **한 줄**만 앞뒤 문맥 없이 인용하면 그 문장이 실제로 무엇을 가리키는
고유명사인지 놓치고 범위를 과잉 일반화할 수 있다.

실측: `DESIGN_workspace_file_placement.md`의 첫 정정(2026-08-01)은 P5의
backlink 절차로 정확한 원본(`symlink-vs-moc-2026-07-30.md`)을 찾아냈다 —
검색은 성공했다. 그런데 "Keep repository and active experiment paths
unchanged"라는 채택 항목 한 줄과, 그 근거 문장("It is unsafe to impose
physically...") 역시 앞의 "Format-first canonical storage"라는 **한정어
없이** 인용해, "활성 실험 폴더 내 어떤 `git mv`도 금지"로 과잉 일반화했다.
원본을 전체 재독(2026-08-02)하자 그 문장이 가리키는 것은 **특정 대안
아키텍처**(정본 저장 + symlink 뷰)를 이 저장소에 이식하는 것이었지,
일반적인 하위 디렉토리 재배치가 아니었다. **찾기와 읽기는 서로 다른
실패 지점**이고, 전자를 고쳤다고 후자가 저절로 맞는 게 아니다.

### P6. **제작자는 자기 결함을 보지 못한다**

**정의**: 결함의 원문이 제작 세션의 컨텍스트에 **이미 있었는데도** 발견되지
않는다. 자체 점검으로 닫히지 않는다 — 가드를 쓴 사람은 그 가드가 필요한
명제를 검사한다고 이미 믿고 있다.

| 리뷰 | 발견 | 비고 |
|---|---|---|
| 1차 (07-30) | blocker #16 외 major 5 | 문제의 계약문 전문이 제작 세션 컨텍스트에 있었다 |
| 2차 (08-01) | blocker 2 + major 7 | 선행사 상실·앵커 유출·영어 tripwire 공백·2-vs-1 |
| 3차 (08-02) | blocker 0, major 2 + minor 1 | Q5~Q8을 **직접 구현한 세션이 놓친** 의역 공백·정확일치 버그·동결 문구 stale — 넷 다 즉시 수정됐지만 발견은 매번 별도 세션이 했다 |

세 리뷰 모두 지시에 **"제작자의 테스트를 증거로 받지 말고 직접 재현하라"**가
있었다. 세 번 모두 제작자 테스트는 **통과 중**이었으므로, 그것을 증거로
받았다면 셋 다 "검증됨"으로 읽혔을 것이다.

## 3. 검증 방법론 — "검증 근거" 칸이 실제로 쓴 방법 8가지

§2의 표마다 "검증 근거" 칸이 있지만 방법 자체는 흩어져 있다. 여기 한 데
모은다 — **각 방법이 무엇을 잡고, 무엇을 원리상 못 잡는지**가 다음에
가드를 새로 짤 때 어느 방법을 쓸지 고르는 근거다.

| # | 방법 | 정의 | 사례(§2 참조) | 원리상 못 잡는 것 |
|---|---|---|---|---|
| M1 | **원문 대조** | 인용된 소스의 실제 바이트를 직접 읽어 주장과 비교 | G1(`sed`로 계약문 두 절 원문 확인), G9, C2, C6, Q9 요청서(칼/철 유일 등장 확인) | 원문이 스스로 거짓을 말하면(P4) 대조해도 못 잡음 — 별도로 "자기서술 vs 실제 동작" 대조가 필요 |
| M2 | **직접 실행/재현** | 코드를 읽지 않고 **실제로 돌려서** 결과를 본다 | G6(렌더 후 `antecedent present? False`), G7(렌더 payload 확인), C4(`_cert_core.run_and_certify` 직접 실행), C8(`git cat-file -e`) | 실행 경로 밖의 분기는 커버 안 됨. "돌려봤다"는 "이 입력에서" 만이지 일반화 아님 |
| M3 | **뮤테이션/주입 테스트** | 정확히 그 실패 사례를 인위로 만들어 가드가 실제로 반응하는지 확인 | G5(대칭 오염 뮤테이션 4종, 1종 LEAKED), G10(3차 리뷰 의역 3종 주입), G11(산문 박힌 type 이름 주입), F7(영어 금지문 주입) | **생각해본 것만** 잡는다(P1 #5·#6). "통과 = 안전"이 아니라 "통과 = 이 주입 세트 안엔 없음" |
| M4 | **양방향 정합성 검사** | A→B뿐 아니라 B→A도 확인(한쪽만 보면 반대편 드리프트를 놓침) | C6(drift 테스트가 원래 단방향이라 H1a가 E2.4에 없는 걸 추가해도 못 잡았음 → 양방향 추가) | 두 방향 다 같은 맹점을 공유하면(같은 저자, 같은 가정) 여전히 못 잡음 |
| M5 | **독립 재구성(별도 에이전트, 제작자 결론 미고지)** | 빌더의 테스트·결론을 증거로 받지 않고 처음부터 다시 유도 | 1~3차 독립 리뷰 전체(P6) — 세 번 다 제작자 테스트는 통과 중이었다 | 리뷰어 1명의 공격 레퍼토리에 갇힌다(§5 "3차 리뷰는 에이전트 1개였다") |
| M6 | **바이트/구조 수준 비교** | 콘텐츠 동일성을 `sha256`·`numstat`·`canonical_json`으로 기계적으로 확정 | Q8(`text_sha256`), Phase 5(`git diff --numstat`의 `0 0`), C9(`MODEL_PAYLOAD_KEYS` 자체를 근거로) | **의미** 동일성은 안 본다 — 바이트가 같아도 문맥이 바뀌면 뜻이 바뀐다(G6, P1 #3) |
| M7 | **인용 대조(발송 전 citation audit)** | 외부로 보내는 문서가 인용한 모든 줄을 실제 파일과 대조 | Q9 요청서 작성 시 인용 3건(doc 102·106행, code 1192행) 실측 대조 | 인용은 맞아도 **해석**이 틀릴 수 있다(P8) — 별도 방법 필요 |
| M8 | **전문 재독(발췌가 아니라 원문 전체)** | 근거 문장 한 줄이 아니라 그 문장을 담은 문서 전체를 다시 읽어 한정어·문맥을 확인 | P8 — `symlink-vs-moc-2026-07-30.md`를 §0.1에서 처음부터 재독, "format-first canonical storage"가 고유명사임을 발견 | 문서 자체가 모호하면(정의가 없거나 흩어져 있으면) 전문을 읽어도 범위가 안 좁혀짐 |

**공통 결론**: 8가지 중 어느 것도 단독으로 충분하지 않았다 — 실제 해결된
28건 대부분이 **최소 2가지 조합**으로 닫혔다(예: G11은 M3로 발견,
M6/M1으로 수정 확인). "검증했다"고 쓸 때는 **이 표에서 몇 번을, 왜
그 조합을 골랐는지**를 함께 적는 편이 "검증함" 한 마디보다 재사용 가치가
크다.

## 4. "이미 다뤄졌는지 먼저 확인" 워크플로 — 단계별 쿼리·리퀘스트·문제 정의

M8(전문 재독)의 상위 절차다. §3이 "찾은 뒤 검증하는 법"이라면 이 절은
**"찾는 절차 자체가 실패하는 지점"**을 단계별로 기록한다. 이번 세션에
실제로 실행된 5개 사례를 그대로 남긴다 — 사후 일반화가 아니라 **실행
순서 그대로**다.

### W-A. skills-catalog에 이 패턴이 이미 있는가 (세션 초반)

**문제 정의**: 새로 발견한 실패 패턴(P7 격)을 skills-catalog에 승격하기
전에, 이미 등재돼 있는지 확인해야 한다 — 중복 등재는 카탈로그의 신뢰도를
깎는다.

| 단계 | 쿼리/리퀘스트 | 결과 | 다음 단계로 넘어간 이유 |
|---|---|---|---|
| 1 | 소수의 영어/한국어 키워드로 `grep`(예: 패턴 이름·핵심 명사 몇 개) | "0건" — 카탈로그에 없다고 결론 | 사용자: "확실히 검증된 것만 추가해라" → "카탈로그를 더 상세히 찾아봐" (얕은 검색이었음을 지적) |
| 2 | 별도 sub-agent에게 **전체 콘텐츠 grep**을 위임 — `~850개 파일`을 키워드 제한 없이 훑도록 지시(59회 tool call) | P1은 **이미 있었다**(내가 07-28에 직접 등재했으나 표를 안 고쳐서 못 찾음), P5는 부분 등재, P7이 실제로 가장 강한 신규 후보 | 종료 — 1단계 결론(P7 "낮은 가치") 을 **뒤집음** |

**이 워크플로가 드러낸 문제**: "grep 0건"은 "없다"가 아니라 "이 키워드
조합으로는 없다"다. 1단계와 2단계의 유일한 차이는 **검색 범위**(키워드
제한 vs 전체 콘텐츠)이지 다른 방법이 아니다 — 범위를 안 넓히면 얕은
검색이 몇 번을 반복해도 같은 결론을 낸다.

### W-B. 활성 폴더 재정리가 이미 결정된 사안인가 (P5 최초 발견)

**문제 정의**: `experiments/2026-07-29_h1a_.../` 안에 `correspondence/`·
`superseded/`를 새로 만들자는 설계를 쓰기 전에, 이미 이 문제에 대한
결정이 있는지 확인해야 한다.

| 단계 | 쿼리/리퀘스트 | 결과 | 다음 단계로 넘어간 이유 |
|---|---|---|---|
| 1 | `rg`로 "디렉토리 정리 / 파일 배치 / DESIGN_DECISION / canonical" 키워드로 **파일명**(경로) 훑기 | 관련 결정 문서를 못 찾음 — 대상 파일 경로가 `notes/audits/vault/symlink-vs-moc-2026-07-30.md`라 네 키워드 중 무엇도 경로 안에 없다(2026-08-02 재확인: `find notes -iname "*canonical*" -o -iname "*design_decision*"`가 이 파일을 반환하지 않음) | 없다고 잠정 결론하고 설계 초안 작성(뒤에 틀린 것으로 드러남) |
| 2 | (사용자 지적 후) `obsidian backlinks path="notes/00-moc/by-topic/vault-architecture.md" counts format=json` | **backlink 2건**: `notes/00-moc/00-vault-home.md`(1), `notes/audits/vault/symlink-vs-moc-2026-07-30.md`(1, status: finished) — 후자가 정답 (2026-08-02 재확인: 위 명령 그대로 재실행, 결과 동일) | backlink 1홉으로 즉시 적중 |

**⚠️ 이 절 자체를 2026-08-02에 재검증하다 부정확한 서술을 하나 잡았다.**
초판은 "그 문서 제목이 1단계 키워드와 교집합 0"이라고 썼는데, **본문
content grep이었다면 사실이 아니다** — 그 문서 본문에 `canonical`이
**8회** 등장한다(`grep -n canonical notes/audits/vault/symlink-vs-moc-2026-07-30.md`
로 재확인). 실제로 안 걸린 이유는 1단계가 **본문이 아니라 파일명/경로만
훑는 검색**이었기 때문이다(원 서술 "파일명만 훑었다"가 정확했는데, 뒤이은
"교집합 0"이 범위를 흐렸다). `rg -l canonical notes/`로 지금 다시 돌리면
이 파일을 포함해 **7개 파일**이 걸린다 — 즉 **본문 content grep이었어도
단서가 됐을 것**이나, 7개 중 어느 게 답인지 순위를 매길 근거가 없어
여전히 graph walk가 필요했을 것이다.

**이 워크플로가 드러낸 문제(P5, 그리고 재검증에서 드러난 하위 함정)**:
결정 문서의 **경로**가 질문의 어휘를 포함하지 않으면 파일명 기반 검색은
원리상 못 찾는다 — 이건 본문 검색과는 다른 실패 지점이다. 여기서 쓴
우회로는 **주제 MOC의 backlink를 역방향으로 탐색**하는 것. 그리고 이
워크플로를 **기록한 문서 자신도**, "본문 검색이 놓쳤다"고 뭉뚱그려 써서
나중에(W-D 스타일 재발) 정정이 필요했다 — 검색 방법을 "파일명 vs 본문"
으로 명시하지 않으면 그 기록 자체가 다음 사람을 오도한다.

### W-C. (W-B의 재발) 그 채택된 결정이 실제로 뭘 금지하는가 (P8 발견)

**문제 정의**: W-B로 찾은 결정 문서를 근거로 "활성 폴더 이동 전부 금지"
설계 문서를 썼다. 사용자가 이 원칙 자체를 재검토해달라고 요청한 뒤, 그
결론이 맞는지 다시 확인해야 했다.

| 단계 | 쿼리/리퀘스트 | 결과 | 다음 단계로 넘어간 이유 |
|---|---|---|---|
| 1 | (W-B에서 이미 찾은 문서의) **근거 문장 한 줄만** 재인용 — "It is unsafe to impose physically..." | "활성 실험 폴더 내 이동 전부 금지"로 해석, `DESIGN_workspace_file_placement.md` §4에 그렇게 기록 | 이것이 이번 W-C의 **1단계이자 원인** — 문서를 다시 찾지 않고 이미 찾아둔 문장만 재사용했다 |
| 2 | `wc -l notes/audits/vault/symlink-vs-moc-2026-07-30.md`(89행 — 전문을 읽을 수 있는 크기인지 확인) | 89행, 전문 재독 가능 | 짧은 문서를 발췌만으로 판단한 것 자체가 낭비였다는 판단 |
| 3 | Read 도구로 **파일 전체**(1~89행) | "Format-first canonical storage"가 그 문서 §"Correction"이 평가한 **특정 아키텍처**(정본 저장 + symlink 뷰)를 가리키는 고유명사임을 확인 — 일반적인 `git mv`가 아니었다 | 종료 — §0.1로 정정, `AskUserQuestion`으로 사용자에게 재확인 후 진행 |

**이 워크플로가 드러낸 문제(P8, W-B와의 차이)**: W-B는 **문서를 못 찾은
것**이었고, W-C는 **문서를 찾아서 인용까지 했는데 그 인용의 범위를
잘못 읽은 것**이다. 같은 "이미 결정됐나" 질문이라도 실패 지점이 다르면
필요한 워크플로도 다르다 — W-B의 해법(backlink 탐색)은 W-C에 안 통한다.
W-C의 해법은 **찾은 문서를 발췌 대신 전문으로 다시 읽는 것**뿐이다.

### W-D. CLAUDE.md에 새 규율을 추가하기 전, 이미 있는 규율인가

**문제 정의**: 사용자가 준 외부 프롬프트 사례(수학 오픈 문제 DB 스타일)를
"문헌 우선 확인" 규율로 추상화해 `CLAUDE.md`에 추가하기 전, 그 규율이나
그것이 언급할 구체적 사실이 이미 다른 문서에 있는지 확인해야 했다 —
방금 추가하려는 규율 자체가 "먼저 확인하라"이므로, 나 자신에게 먼저
적용하지 않으면 그 규율을 쓰는 순간부터 위반이 된다.

| 단계 | 쿼리/리퀘스트 | 결과 | 다음 단계로 넘어간 이유 |
|---|---|---|---|
| 1 | `grep -n "^## \|^### " docs/HARNESS_KNOWHOW.md` — 재사용 노하우 문서의 목차만 훑기 | B4·B5·B7이 내가 쓰려던 패턴과 이미 겹침을 확인 | 완전한 중복은 아니었으므로(문헌 검색이라는 관점은 새로움) 계속 |
| 2 | `grep -rn "owlready2" docs/*.md CLAUDE.md` — 곧 쓰려던 구체적 사실(게이트의 기존 FAIL)이 이미 문서화됐는지 | `E2.4_ISSUE_REGISTER.md`·`HANDOFF.md` 등 5곳에 이미 있음 | 있었지만 **어디에**(몇 번째 줄)인지가 관건이라 다음 단계로 |
| 3 | `awk '/^## /{h=NR": "$0} NR==685{print h}' docs/HANDOFF.md` — 685행이 어느 섹션 밑인지 | "## 9. 검증 명령" 아래, 920행짜리 문서의 685행 | 종료 — "없다"가 아니라 "있지만 필요한 순간에 안 보이는 자리"라는 **다른 종류의 문제**로 재정의(`NEXT_SESSION_TRAPS.md` §0으로) |

**이 워크플로가 드러낸 문제(신규, P5·P8과 다른 세 번째 변종)**: 1·2단계는
"찾았다/없다"를 답했지만 그것만으로는 충분한 정보가 아니었다. 3단계가
**위치(도달성)**를 재는 것으로 질문 자체를 바꿨다 — "이미 다뤄졌는가"의
답이 "예"여도, "필요한 순간에 닿는가"는 별도로 재야 하는 질문이다.

### 공통 절차 (4개 사례에서 반복된 뼈대)

```
1. 좁은 키워드로 첫 시도(grep/rg) — 비용이 가장 싸다
2. "0건"이 나오면: 그것을 "없다"로 읽지 말고 "이 범위로는 없다"로 읽는다
3. 범위를 넓히는 두 가지 축 중 하나를 고른다
   - 검색 폭 확장: 전체 콘텐츠 grep(W-A), 별도 sub-agent 위임
   - 검색 방식 전환: lexical → graph walk(W-B), 발췌 → 전문 재독(W-C)
4. 답이 "있다"로 나와도 멈추지 않는다 — 위치(도달성, W-D)와 범위(문맥,
   W-C)를 별도로 확인한다
5. 결론이 이전 결론을 뒤집으면, 그 사실 자체를 기록한다(이 문서 §2.1의
   W5·W6, W-A의 P7 사례처럼) — 뒤집혔다는 것 자체가 다음 세션에게
   "1단계만 믿지 말라"는 신호다
```

**이 문서가 스스로 이 절차를 어긴 사례**: W-C는 애초에 W-B의 결과를
**2단계(범위 확장) 없이 1단계 인용만으로 결론 내려던 것**이었다. 위
절차의 4번("답이 있다로 나와도 멈추지 않는다")을 건너뛴 결과였다.

### W-F. 이번(압축 이후) 세션이 실제로 `rg`/grep과 obsidian CLI를 각각 썼는가 — 자기감사

**문제 정의**: 사용자가 "최근에 문서 검색을 했을 때 rg 키워드 검색과
obsidian CLI wikilink 타기를 했었는지" 직접 물었다. 짐작으로 답하지 않고
**이번 대화의 압축 이후 구간에서 실제로 실행한 도구 호출을 전수 감사**한다.

| # | 확인 대상("이미 다뤄졌나" 질문) | 실제로 쓴 방법 |
|---|---|---|
| 1 | CLAUDE.md에 "문헌 우선 확인" 규율을 추가하기 전(W-D) | `grep`만 3회(HARNESS_KNOWHOW 목차, owlready2, repo_root) |
| 2 | `DESIGN_REQUEST*.md`를 `correspondence/`로 옮겨도 되는가(Phase 5) | `grep`만(어떤 `.py`도 로드 안 함 확인) |
| 3 | Q9 요청서 인용 3건이 실제 원문과 맞는가 | `grep -n`만(정확한 줄 대조) |
| 4 | `NEXT_SESSION_TRAPS.md`를 쓰기 전 기존 문서 중복 확인 | `grep`·`wc -l`·`awk`만 |
| 5 | `README.md`가 낡은 서술을 담고 있는가(§7.1) | `grep -c`만 |
| 6 | `e2.2-wt` 사본과의 드리프트 | `diff -rq`(grep도 obsidian도 아님) |
| 7 | `notes/`에 `DESIGN_REQUEST` 미러가 있는가 | `find`만 |
| 8 | (지금) W-B 절의 정확한 키워드·backlink 수 재검증 | **obsidian CLI 처음 사용**(`vaults verbose`, `backlinks ... counts format=json`) — 단 이건 **새 "이미 다뤄졌나" 확인이 아니라 과거 주장의 재검증**이었다 |

**결론 — 정직한 격차**: 1~7번 **일곱 건 전부 `grep`/`find`/`diff`만
썼고, 단 한 번도 obsidian CLI backlink를 능동적으로 쓰지 않았다.**
이 문서 §4가 스스로 처방한 절차(3단계: "범위를 넓히는 두 축 — 검색 폭
확장 **또는** graph walk")에서, 이번 세션은 매번 "검색 폭 확장"(더 넓은
grep) 쪽만 택했고 graph walk 쪽은 한 번도 안 갔다. 이유를 사후 추정하면:
1~7번 전부 **grep이 첫 시도에서 바로 답을 줬다**(빈 결과든 히트든
명확했다) — graph walk는 "grep이 애매하거나 0건인데 문서가 있을 법할 때"
쓰는 두 번째 수단인데, 이번엔 그 조건이 한 번도 걸리지 않았다. **그러나
이것 자체가 검증되지 않은 가정이다** — grep이 준 "빈 결과"·"낡음 확인"
답이 실제로 완전했는지 graph walk로 교차검증한 적이 없다. W-B/W-C의
교훈("찾았다고 멈추지 마라")을 이번 세션 자신에게 적용하면, 1~7번 중
최소 하나는 obsidian backlink로 교차검증해 볼 가치가 있었다는 뜻이다.
