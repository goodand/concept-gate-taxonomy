### A. I30 — 문서가 구현을 앞섰다 (P1 11번째, 해결)

#### (5) 문제 정의

가드의 **선언**과 **구현**은 서로 독립적으로 존재할 수 있고, 통과하는 쪽에서
보면 **관측값이 같다.** `tracked_file_count()`가 정의돼 있고 docstring이 그것을
G4로 인용하면, 코드를 읽는 사람은 G4가 동작한다고 읽는다. 호출부가 없어도
테스트는 전부 초록이다 — 없는 가드는 아무것도 실패시키지 않으므로.

이것은 I29(사전등록 "✅ 자동" 10건 중 4건만 참)와 **같은 패턴의 코드판**이다.
쓰는 시점과 구현하는 시점이 달라서 생기며, 나쁜 의도가 필요 없다.

#### (6) 가설 및 검증 방식

- **가설 H30**: docstring이 선언한 가드 중 실행 경로에 없는 것이 있다.
- **검증**: 선언된 각 가드 이름에 대해 정의부와 **호출부를 따로** grep.
  ```
  94:def tracked_file_count() -> int:   ← 정의 1건
  (호출) 0건                            ← G4 부재 확정
  while                                 ← 파일 전체 1건, reachable_from 내부
                                          → main()은 단발, G5 부재 확정
  ```
- **반증 조건**: 호출부가 1건이라도 나오면 H30은 그 가드에 대해 기각.

#### (7) 해결 방법

1. **docstring을 먼저 고쳤다.** 구현보다 정정이 먼저다 — 커밋된 도구가 거짓을
   말하고 있는 상태를 한 순간이라도 유지하지 않기 위해. `STATUS AFTER
   ADVERSARIAL REVIEW` 절에 "다섯을 선언하고 셋을 구현했다"를 명시.
2. G4 실구현 — `assert_input_not_narrowed(before)`:
   - `tracked_file_count()` 감소 검출
   - `audit_input_set(ref)`에서 이탈한 멤버 검출
   - `skip_worktree_paths()` 비어있지 않으면 거부
   - **raise가 아니라 violations 리스트 반환** — 한 번 실행으로 전부 보고.
3. `--emit-pins`가 해시**만** 내던 것을 `{hashes, tracked_file_count, ref,
   audit_inputs}` 한 덩어리로 변경. **한쪽만 잊는 것을 구조적으로 불가능하게.**
   베이스라인 없는 구버전 pins가 오면 그 자체를 위반으로 보고한다.
4. G5 실구현 — `--require-progress PREV`, `total >= PREV`면 STALL로 종료.
5. `.gitignore`를 PINNED에 추가.

### B. I38 — 메타 테스트가 공허했다 (P1 12번째, **부분 해결**)

#### (5) 문제 정의

"정의됐지만 호출되지 않음"을 검출하려는 테스트가 **함수 이름이 소스에
등장하는지**를 검사했다. 그런데 `def tracked_file_count()` 한 줄이 이 조건을
만족한다. **검출하려는 결함 자체가 검사를 통과시킨다.**

일반화하면: **문자열 검색은 "존재"를 보지만 P1이 묻는 것은 "역할"이다.**
이름의 존재와 호출의 존재는 텍스트 수준에서 구별되지 않는다.

#### (6) 가설 및 검증 방식 — 이번 구간에서 유일하게 성공한 기제

음성 테스트를 쓴 것으로 끝내지 않고, **결함을 되살려 테스트가 잡는지** 봤다.

| 뮤테이션 | 기대 | 실제 | 판정 |
|---|---|---|---|
| G4 호출부 삭제 (= I30 원본 재현) | 실패 | **통과** | **공허** |
| G5 플래그를 안 읽게 (`if False:`) | 실패 | 실패 | 유효 |
| G2를 줄 세기로 되돌림 | 실패 | 실패 | 유효 |
| `KNOWN UNCLOSED BYPASS` 문단 삭제 | 실패 | 실패 | 유효 |

4건 중 1건이 공허였고, **하필 그 1건이 원래 결함을 정확히 재현한 것**이었다.
나머지 3건이 전부 유효했기 때문에, 뮤테이션을 안 돌렸다면 "음성 테스트를
갖췄다"는 결론이 나왔을 것이다.

**이 표가 이번 회고의 핵심 산출물이다.** 규율(리뷰, 대조, 체크리스트)은 12번
실패했다. 뮤테이션은 첫 적용에서 잡았다.

#### (7) 해결 방법

```python
called = {
    node.func.id
    for node in ast.walk(ast.parse(src))
    if isinstance(node, ast.Call) and isinstance(node.func, ast.Name)
}
assert func in called, f"{guard}는 IMPLEMENTED로 문서화됐으나 {func}()가 호출되지 않는다"
```

문자열 검색 → **AST `ast.Call` 노드 요구**로 교체. 정의는 `ast.FunctionDef`라
집합에 들어가지 않으므로 구별된다. 테스트 docstring에 이 사고 자체를 기록해
다음 사람이 문자열 검색으로 되돌리지 않게 했다.

**재뮤테이션 검증(실측)**: 교체본에 같은 뮤테이션(G4 호출부 삭제)을 다시 적용.
이번에는 K2 권고를 스스로 적용해 **뮤테이션이 실제로 바이트를 바꿨는지 먼저
assert**하고(no-op 뮤테이션이면 "검출 실패"가 "정상"으로 부호가 뒤집히므로)
실행했다.

```
뮤테이션 적용 확인: 바이트 변경됨
E  AssertionError: G4 is documented as IMPLEMENTED but
   assert_input_not_narrowed() is never called. A definition is not an
   implementation.
1 failed, 8 passed        ← 문자열판은 여기서 통과했었다
복원 후 24 passed
```

**같은 입력에 대해 문자열판은 통과, AST판은 실패.** 이 대조가 교체의 실효성
증거다. I38 해결.

### C. I31 — 소스를 핀하고 바이트코드를 실행한다 (**미해결, 공개 처리**)

#### (5) 문제 정의

무결성 핀은 **실행되는 것**을 고정해야 하는데, G1은 **읽히는 것**을 고정했다.
CPython에서 두 개는 다른 파일이다. `__pycache__/`는 gitignore 대상이라
`git status`에도 안 나온다.

#### (6) 가설 및 검증 방식

- **가설 H31**: 소스를 복원한 채 바이트코드만 바꾸면 G1을 통과한다.
- **검증(red team 실행)**: 패치한 `audit()`를 `py_compile`로 hash-based
  **UNCHECKED** `.pyc`로 컴파일 → 소스를 바이트 단위 복원 → 실행.
- **결과**: 핀 해시 완전 일치, `git status` 깨끗, 마크다운 편집 0건, **PASS**.
- **부수 확인**: `python3 -B`는 방어가 아니다 — **쓰기만 막고 읽기는 안 막는다.**

#### (7) 해결 방법 — 가드가 아니라 아키텍처

in-process 가드로는 원리적으로 못 막는다. 채점기를 `import`하는 한, 채점기를
실행하는 프로세스가 **이미 오염돼 있을 수 있기** 때문이다. 필요한 것은:

```
subprocess + -B -E -P -I + __pycache__ 제거/리다이렉트
그리고 해시 검증을 그 subprocess "안"에서 수행
```

순서가 결정적이다. 더러운 프로세스 안에서 해시를 검증하면 검증 자체가 조작
대상이다. **이번 세션 범위를 넘으므로 구현하지 않고 공개했다** —
`KNOWN UNCLOSED BYPASS` 절 + 그 절의 삭제를 막는 테스트.

공개 문구의 요지: **"green run은 문서에 대한 증거이지, 채점기가 조작되지
않았다는 증거가 아니다."** 이것은 이 저장소의 `pass-is-a-conjunction` 규율
(검증 못 하는 조건은 이름을 붙여 남기고 통과로 세지 않는다)을 그대로 적용한
것이다.

  치환. **도달 파일 수를 지표와 별도로 측정** — 135 → 135.
- **핵심**: 도달 파일 수라는 **독립 관측량**이 있었기에 지표 하락이 가짜임을
  보일 수 있었다. 지표만 봤으면 성공으로 읽혔다.

#### (7) 해결 방법

- **I32 해결**: 베이스라인에 `tracked_file_count`와 `audit_inputs`를 함께
  동결하고, 실행 후 **집합 차집합**으로 이탈 멤버를 이름까지 지목해 보고.
  음성 테스트 3건(삭제 / gitignore / skip-worktree) + 위양성 테스트 1건.
- **I33 미판정**: mention을 dangling으로 보고하지 않는 것은 404 위양성을 고친
  **옳은 결정**이었고(K5), 그 결정이 게임 경로를 만들었다. 두 요구가 실제로
  충돌하므로 임의로 정하지 않고 **설계 문제로 등록**했다. 하네스 개발자에게
  이 변환을 adversarial case로 넣기를 권고했다.

## 이 회고가 남기는 방법론적 사실

1. **P1은 12회가 됐고, 12번째는 그것을 잡으려는 테스트 안에서 났다.**
   대상 코드의 버릇이 아니라 검사를 쓸 때의 기본 기울기다.
2. **음성 테스트의 존재를 강제하는 기제는 있으나 실효성을 강제하는 기제는
   없었다.** `test_guard_negative_coverage.py`가 그 틈을 남긴다.
3. **그 틈을 메운 것은 뮤테이션이었다.** 4건 중 1건이 공허했고, 그 1건이
   하필 원래 결함의 재현이었다. 규율은 12/12 실패, 뮤테이션은 1/1 성공.
4. **제작자 맹점 6번째.** 신규 10건 중 8건을 외부(red team)가 찾았다. 나머지
   2건(I38, I39)은 제작 세션 쪽에서 났는데, **둘 다 사람이 아니라 기제가
   찾았다** — I38은 뮤테이션이, I39는 `test_guard_negative_coverage.py`가.
   리뷰·대조·체크리스트가 찾은 것은 이번에도 0건이다.
5. **음성-커버리지 게이트가 처음으로 사전 작동했다.** 지금까지 이 게이트는
   기존 코드를 소급 점검했다. 이번엔 **이 세션이 방금 쓴 파일**에서
   `assert_pins_intact`의 음성 테스트 부재를 커밋 전에 잡았다(I39). 기제를
   한 곳에 커밋해 전파시키라는 규칙의 실측 이득이다.
6. **고칠 수 없는 것을 고친 척하지 않았다.** I31은 아키텍처 문제라 공개로
   처리하고 그 공개가 지워지는 것을 테스트로 막았다.
