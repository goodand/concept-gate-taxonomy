### A. 공허한 가드 (I2 → I16)

**(5) 문제 정의**: 가드 함수는 두 명제를 동시에 보장해야 한다 — "위반 입력에서
발동", "정상 입력에서 통과". 긍정 테스트만 있으면 이 두 상태의 **관측값이
동일**하다:

```
정상 가드     : 정상→pass ✅, 위반→raise ✅
공허한 가드    : 정상→pass ✅, 위반→raise ❌   ← 긍정 테스트로는 구별 불가
```

`assert_5`(owl)가 1차 발생, `assert_9`(h1-wt)가 재발 — 단 `assert_9`는 완전
공허는 아니고 **raise 경로 3개가 코드 구조상 도달 불가**라는 변종.

**(6) 가설/검증**: 가설 — "가드 존재 = 안전"이라는 가정이 틀렸다. 검증 —
① 진리표로 관측 불가능성을 도출(사고실험) ② AST 정적 분석으로 실제
코드베이스의 `assert_*`/`_assert_*` 함수 전수 수집 ③ `pytest.raises` 안에서
호출되는지 대조해 미커버 목록 산출 ④ 실제 `pytest -q` 실행으로 owl 10/10,
h1 18/16→17/18 수치 확보.

**(7) 해결 방법**: `test_guard_negative_coverage.py`(repo root, import 없이
AST만 사용 — 실험 폴더 동명 모듈 `sys.modules` 충돌 회피)를 만들어 root
`pytest -q`가 자동 수집하도록 배선. 도달 불가 경로는 모킹으로 날조하지 않고
`KNOWN_UNPROVEN: dict[str, str]`에 이름→이유→담당을 등재하고, 그 목록 자체의
staleness(가드가 사라지거나 커버되면 자동 실패)를 검사하는
`test_known_unproven_entries_are_not_stale`를 추가. owl에 커밋(`d8db0eb`),
CLAUDE.md에 "가드를 쓰면 음성 테스트가 함께 온다" 절 신설(`95333e3`). h1-wt의
`assert_9`는 D-H1a-12 Q12.4 판정에 따라 독립 golden contract
(`h1a_common_policy_block_v2` + sha256, 음성 테스트 5종)로 대체 예정 —
**아직 미구현**.

### B. args 문자열 함정 (I6)

**(5) 문제 정의**: Dynamic Workflow 스크립트에 `args`로 객체를 넘기면 실행
시점에 **문자열로 도착**해 `args.templates[arm]` 같은 접근이 `undefined`가
되어 조용히 실패한다(`agent_count: 0, duration: 77ms`). 3회 반복 실패.

**(6) 가설/검증**: 가설 — args 채널이 JSON 파싱 없이 원문 텍스트로 전달된다.
검증 — 실패 시 에러 메시지를 그대로 기록·대조(3회 동일 패턴 확인), 그 다음
데이터를 스크립트 리터럴로 직접 박아 넣은 버전을 만들어 `journal.jsonl`에
실제 trial 결과가 기록되는지로 성공 여부 판정.

**(7) 해결 방법**: `const RENDERED = {...}; const TRIALS = [...]; const
SCHEMAS = {...};`처럼 데이터를 스크립트 본문에 리터럴로 직접 embed하고
`Workflow({scriptPath})`로 실행. 이 패턴이 `owl_cohort_workflow.js` 주석에
근거(`OPERATIONS_LOG.md` §5 인용)로 남았고, 이후 세션 2가 독립적으로 이
함정을 안 밟은 것(N=16 스크립트도 동일 패턴 사용)으로 외부 검증됨.

### C. 운영 개입 과잉 (I1 → I11)

**(5) 문제 정의**: 실험 "기획·운영자" 역할이 "판정자" 역할과 섞이면, 자기
결함을 스스로 통보하는 순간 "자기 결함을 스스로 잡는가"라는 관측 지표 자체가
소멸한다. I1은 상신용 리뷰를 과다 생성한 사례, I11은 세션 2의 결함 4건을
판정 없이 바로 전달하려 한 사례 — 같은 "역할 경계 침범" 패턴.

**(6) 가설/검증**: 가설 — 두 역할을 겸하면 관측이 오염된다. 검증 — 사용자의
직접 지적("개입 너무 많은 거 아니야?") 자체가 반증 사례 발견이었고, 이후
"판정만 하고 수정 지시는 하지 마"라는 명시적 제약 부여 후 실제로 4개 결함
목록을 세션 2에 전달했는지 재확인(전달하지 않은 것을 로그로 확인) — 미전달이
유지됨으로써 역할 분리가 실제로 지켜졌음을 검증.

**(7) 해결 방법**: 역할을 "판정만"으로 명시 축소하고, 발견한 4건은
`OPERATIONS_LOG.md`에만 기록하고 세션 2에는 전달하지 않음 — 그 결과 트리거
실험의 2차 지표(자기 결함 자가 포착)가 0/4로 순수 관측됨.

### D. worktree 손복사 시도 (I14)

**(5) 문제 정의**: worktree들은 **하나의 git 저장소를 공유**하므로 파일이
다른 worktree에 도달하는 정상 경로는 커밋→머지→rebase지, 손으로 복사하는 게
아니다. 그런데 이 세션이 repo 전역 게이트 파일을 "worktree마다 넣어야 할
파일"로 오인해 두 번 시도했다 — ① h1-wt에 직접 쓰기 시도(격리 도구가 거부)
② h1-wt·owl-wt에 준비물 번들을 각각 복사하려던 계획.

**(6) 가설/검증**: 가설 — 손복사는 CLAUDE.md가 이미 없앤 "사본 두 벌 → 한쪽만
수정 → 거짓 통과" 실패 모드를 재현한다. 검증 — 실제로 Write/Edit 도구가
owl-wt 밖 쓰기를 거부하는 에러 메시지를 직접 관찰(①), 그리고 커밋·푸시 후
별도 세션의 `vault_search`가 그 문서를 rank 1로 찾아내는 것으로 정상 전파를
확인(②의 대안 경로 검증).

**(7) 해결 방법**: 준비물 번들을 폐기하고, `CLAUDE.md`에 "worktree 간 손복사
금지, 커밋 전파" 규칙을 30줄 append-only로 신설(`concept-gate-owl-wt/CLAUDE.md`).
이후 D-H1a-12는 owl에 커밋 후 "h1-wt로 cherry-pick 필요"라고 문서 헤더에
명시하는 방식으로 처리 — **단, 실제 cherry-pick 자체는 아직 실행되지
않았다.** 규칙 확립과 방법 준수는 확인됐지만, h1-wt로의 실제 전파는 남은
작업이다.

### E. 검색 recall 실패 (I10 → I21)

**(5) 문제 정의**: "이미 결정된 것을 찾는" 실패(문서가 있는데 검색 안 함)와
"지금 쓰는 것을 검사하는" 실패(가드에 검사가 없음)는 **다른 종류**다. I10은
전자(H1a 문서 문장을 owl 것으로 오귀속, 검색 없이 단정), I21은 스킬
description을 TRIGGER 형식으로 개선한 뒤에도 "가드 작성"이라는 명시된 트리거
상황에서 검색이 발동하지 않은 사례.

**(6) 가설/검증**: 가설 — description을 TRIGGER/SKIP 명령형으로 재작성하면
recall이 개선된다. 검증 — 완전히 새로운/맥락 없는 세션에, 실험 산출물이 아닌
**버려도 되는 자극**을 주고, 프롬프트에 "검색"·"트리거" 등 단어를 넣지 않은
