## (5)(6)(7) 상세 — 반복 O + 해결근거 O

### A. I40 — 충돌 0건이 안전을 뜻하지 않는다 (해결)

#### (5) 문제 정의

병합 안전성 판정에 **CONFLICT 개수**를 썼다. 그러나 git의 rename 탐지는
충돌을 만들지 않고 **조용히 잘못된 병합**을 수행할 수 있다.

`input-length-guard` worktree의 유일한 고유 커밋은 `CLAUDE.md` →
`CLAUDE.legacy.md` 격리 rename이었다. 여기에 활성 `CLAUDE.md`를 수정한
브랜치를 병합하면 git은 rename을 추적해 **수정분을 격리 문서 안으로 밀어
넣고 활성본을 삭제**한다. 충돌은 0건이다 — git 입장에서는 모순이 없기
때문이다.

일반화: **"도구가 오류를 보고하지 않았다"는 "결과가 옳다"가 아니다.**
도구가 무엇을 검사하는지와 내가 무엇을 알고 싶은지가 다를 수 있다.

#### (6) 가설 및 검증 방식

- **가설 H40**: 충돌 0건인 병합이 파일 내용을 잘못 만들 수 있다.
- **검증**: `git merge-tree --write-tree`로 결과 트리를 얻고, 파일별
  **blob sha를 기준 blob과 대조**. 충돌 수를 보지 않는다.

| | rename 탐지 ON(기본) | `-Xno-renames` |
|---|---|---|
| CONFLICT 수 | **0** | 1 (modify/delete) |
| `CLAUDE.md` | **트리에 없음** | `120f5900d6` = 활성본 |
| `CLAUDE.legacy.md` | `5ae2a79e21` (17,661B, 오염) | `7c9c7f8b90` = 원본 |

- **반증 조건**: 두 blob이 기준과 일치하면 H40은 이 사례에서 기각.
  일치하지 않았으므로 성립.

#### (7) 해결 방법

1. **판정 기준을 교체했다.** 충돌 수 → 결과 트리의 blob sha 대조. 병합
   실행 전에 항상 이 검사를 먼저 한다.
2. rename으로 격리한 문서가 있는 트리에는 **`-Xno-renames` 필수**로
   커밋 메시지에 명문화(`a9816fa`, `5013580`).
3. 검사 코드 자체의 결함(I42)도 이때 드러났다 — `git rev-parse`가 실패 시
   입력을 되돌려주는 것을 몰라 폴백이 안 걸렸다. `git ls-tree`로 교체.

### D. I50 — 모킹이 못 잡은 것을 실행이 잡았다 (해결, 신규 패턴)

#### (5) 문제 정의

`vault-backlinks-mcp`는 21개 단위 테스트를 전부 통과한 상태였다. 그 테스트는
`graph_for_candidate`를 **모킹**해 `[{"file": ..., "count": ...}]` 형태만
돌려줬다. 그런데 실제 harness의 `parse_cli_output()`은 JSON 파싱에 실패하면
**문자열 리스트**로 폴백한다. `contracts.py`는 `item.get("file")`을 호출해
`AttributeError`로 크래시했다.

**모킹은 내가 상상한 계약을 검증하고, 실행은 실제 계약을 검증한다.** 21개
초록이 이 결함에 대해 말해주는 것은 없었다.

#### (6) 가설 및 검증 방식

- 이 결함은 가설을 세워 찾은 것이 **아니다.** 통합 실험에서 두 번째 vault
  (`goodantak`)를 실제로 조회하다 크래시로 드러났다.
- **핵심**: 첫 vault(`project-in-progress`)만 조회했으면 안 났다. 정본이 아닌
  경로를 가진 vault가 있어야 폴백 경로가 발동한다.

#### (7) 해결 방법

1. `isinstance(item, str)` 분기 추가 — 문자열이면 `{"file": item}`으로
   승격, dict도 문자열도 아니면 drop.
2. **회귀 테스트 추가** — 실제로 발생한 형태(`["docs/source.md"]`)를 그대로.
3. 통합 프로브(`integration_probe.py`)를 만들어 **3개 vault 전부**에 실서버를
   돌린다. 평면형/symlink형/둘 다 아닌 것 — 서로 다른 모양이어야 폴백 경로가
   드러난다.

## 이 회고가 남기는 방법론적 사실

1. **P1은 15회가 됐고, 13·14·15번째는 전부 같은 세션 안에서 났다.** 12번째의
   교훈(뮤테이션을 써라)을 적용한 직후에도, 새 테스트를 쓸 때마다 다시 났다.
   앞선 검사가 유효했다는 사실은 **다음 검사에 아무 보장도 주지 않는다.**
2. **뮤테이션은 4/4 성공했다.** I49, I51, I52 전부 뮤테이션이 잡았고, 각
   수정 후 재뮤테이션으로 실효성을 확인했다. 이 구간에서 리뷰·대조가 찾은
   결함은 0건이다.
3. **양방향 확인이 결정적이었다(I51).** 수동 집계가 찾은 방향만 고쳤으면
   더 위험한 반대 방향(과확신)이 계속 미검출로 남았다. **"이 검사가 못 잡는
   다른 방향은?"을 매번 물어야 한다.**
4. **모킹 맹점이 처음 기록됐다(I50).** 21개 단위 테스트 초록 상태에서 실환경
   두 번째 케이스가 크래시했다. 단위 테스트는 상상한 계약을, 통합 실행은
   실제 계약을 검증한다 — 둘 다 필요하다.
5. **사용자 지적 2건이 모두 "확정"이라 쓴 판정을 뒤집었다(I43, I44).** 둘 다
   현상 하나에 설명 하나를 붙이고 대안을 배제하지 않은 것이 원인이다.
   "확정"이라 쓰기 전에 **통제하지 않은 변수가 있는지** 물어야 한다.
6. **실험 결과가 설계를 소급 수정하지 못하게 하는 규율이 실제로 작동했다.**
   I51은 결과를 본 직후에 발견됐고, 고치고 싶은 유혹이 정확히 그 순간에
   가장 컸다. `evaluate.py`를 그 커밋에서 건드리지 않고 amendment로 분리한
   뒤, 별도 커밋에서 A·B를 제외한 `Z6`으로 구현해 **기존 수치 불변**을
   확인했다.
7. **사전등록 실험이 실제로 도구 결함을 고쳤다.** T1/T2에서 Z2 3-4/5였던
   것이 docstring 수정(T3) 후 1/5, D case는 3/5 → 0/5. 남은 1건은 읽어보니
   **다른, 더 방어 가능한 실패 모드**(어느 파일이 조회됐는지에 대한 회의)
